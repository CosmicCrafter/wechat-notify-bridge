# 工程案例：从单一通知到多会话准确路由

**工程案例 · 基于 F02 与当前 1.18.0 实现。** 场景是一个应用同时被两个 AI 聊天使用，管理员还可能主动发起第三个会话。它们不应为每次聊天申请新应用 Key，也不能因“现在只有一个任务等回复”就把一句裸文本交给它。

## 原方案的局限

legacy 会话能用 conversation_id 和显示标签分流，但共享 Key 只有应用级认证。持同一 Key 的调用方不能据此证明自己是某个真实 AI 窗口。显示名又可修改，不宜作为消息和接收权限的持久主键。仅有一个待答任务时猜目标，会把弱上下文误当作用户选择。

这是兼容机制的能力边界；本次没有删除旧 Key 或要求所有旧客户端迁移。问题在于不能把应用认证宣传为聊天强身份。

## 设计选择与取舍

应用 client_id、会话 conversation_id、具体通信 bot_id、protected 接收能力分别承担稳定身份、记录归属、传输目标和接收授权。一次登记返回真实会话 ID，同一个稳定 conversation_key 重试复用。管理员主动创建可以先存首条消息，稍后由接收端配对。

![protected 会话分开检查应用和会话能力](../assets/receiver-boundary.svg)

私有能力文件使服务能拒绝错会话和观察者写操作；它并不证明操作系统用户或聊天窗口。选择“校验可验证的能力持有”而不伪造宿主证明，保留真实宿主限制。原理与操作分别见[可靠收件](../explanations/RELIABLE-CONVERSATIONS.md)和[绑定步骤](../integration/RECEIVERS.md)。

## 实际实现

`api/receivers.py` 逐次检查应用认证、能力与请求会话；`storage/receivers.py` 保存绑定、配对和撤销状态。元数据与内容权限分开，观察者可读不能领取。主密钥/应用 Key 不通过模型上下文传递。

飞书引用回复用上游原消息映射找会话；卡片按任务、消息、Bot、本人共同校验。未知/含糊标签和无明确引用的裸文本进入待归属，不猜唯一任务。这个变更经过用户明确选择；显示名不参与 protected 内容授权。

## 如何验证

现有 `test_f02_receivers.py::test_one_app_two_scopes_no_extra_app_key_and_cross_conversation_denied` 使用同一应用登记 A/B，断言凭据数量未增加；缺能力、另一应用或 B 能力读取/领取 A 均被拒绝。管理员首条消息、一次性交换、观察者与撤销分别有定向测试。

`test_f02_inbound.py` 覆盖裸文本不猜单个输入任务、父消息映射和重新归属的授权检查。R2/R3 历史摘要有特定 Codex 主动调用与真人双向验证；[证据索引](EVIDENCE.md)区分历史结论与本轮复验。两份代码测试和一次平台验收不能推导全宿主身份保证。

## 已知限制

- 同用户下能读同一私有文件的进程可能持有相同能力，无法据此保证真实 AI 窗口隔离。
- legacy 只保留应用级范围；不能去掉接收头后把请求降级成合法 protected 访问。
- 平台收件和宿主自动唤醒分开，连接成功不恢复外部旧聊天窗口。
- 未在本轮做多租户、群聊或吞吐压力测试；没有对应性能/SLA 声明。
