# 工程案例：人类与 AI 双友好的文档交付

**工程案例 · REFINE-01 → DOC-01 → DOC-02。** 使用者希望把一个文档网址交给 AI，不先教它找 Markdown；管理员同时需要私密接入包，普通开发者需要可运行 HTTP 示例。网站、仓库和插件若各自维护同一套事实，很容易出现菜单、版本和安装说明互相冲突。

## 原方案暴露的问题

早期有效 API 说明混有历史版本段落、重复参数表与管理操作；导出包可能包含不相关历史。只检查 Markdown 并不能证明网站里读到的是同一版本，包能下载也不能证明解压后的安装脚本独立可用。只靠浏览器 JS 生成正文还会让不能运行脚本的读者/AI 看见空壳。

一次原生 Codex 补丁审查发现，独立插件 ZIP 内的重建脚本依赖包外仓库文档；文件存在于开发机不代表用户解压后可运行。这是交付边界错误，而非通过美化页面能解决的问题。

## 选择与取舍

保留现有 Markdown、FastAPI OpenAPI、Skill 和标准库示例；继续使用现有 marked、构建器和公开路由，不另建文档平台。DOC-01 的布局与本地脚本只增强阅读，正文、链接和图仍在静态 HTML 中。DOC-02 把接口字段投影为生成参考，把教程、操作、原理、案例分开。

```text
实现 / OpenAPI ─→ 生成请求字段合同 ─┐
Markdown / Skill / 示例 / 静态图 ──┼→ 用途白名单 → HTML / Markdown / llms.txt
版本与公开源指纹 ─────────────────┘              └→ 后台正文 / 文档 ZIP / 接入模板
实例私有配置 ── 只在鉴权导出阶段加入，绝不进入匿名站点或公开构建
```

图中文字表达的是构建关系，不意味着所有私有包拥有相同指纹；fingerprint_scope 明确各用途的公开输入范围，不能拿文档包指纹直接比较带凭据的整个 ZIP。

## 实际实现

build_developer_kit 按白名单生成资料；同一 ai_index 函数分别投影网站路径和包内路径。原 OpenAPI 生成请求参考，未声明完整响应模型的部分保留“未声明”，不补写猜测。公开 Skill 是维护源的只读投影，私有文件和运行数据不在输入集合。

公开路由只读构建工件；管理数据、消息、原 /openapi.json 和私密导出仍保持鉴权。SVG 仅允许静态图元、有限属性和本地标记引用，构建拒绝脚本、外部加载及活动内容。前端不需要 Mermaid 运行库、远程字体或 CDN。

独立包重建时，仓库规范优先；只有解压包确实没有仓库标识才使用包内生成说明，不能在维护仓库缺源时静默退回过期副本。DOC-02 还实际发现安装说明新增相对链接会在专用包中失效，修正包内引用与按用途阅读入口，继续让链接守卫失败关闭。

## 验证方法和证据

验证分为源检查、构建/解压、HTTP 权限、浏览器和新 AI 使用五层。反向测试故意破坏版本、字段说明、索引、必需文件、链接和源摘要，检查必须失败，而不是仅证明正常输入能通过。

1.18.0 的[公开 Linux/Windows CI](https://github.com/CosmicCrafter/wechat-notify-bridge/actions/runs/38778810721)对应 a33517f，包含当时 428 项 Python 测试与包检查。DOC-01 的 443 项属于后续本地验证，不冒充新托管 CI。新 AI 只给根网址的接手流程和 SDK/真人层级另见[证据索引](EVIDENCE.md)；本轮实际结果在 DOC-02D 记录。

## 已知限制

自持轻量生成器降低了框架迁移成本，也意味着新增媒体、链接与打包用途必须有检查。摘要用于一致性，不是防拥有仓库修改权限者篡改整条流水线的安全签名。公开可读不等于每个 AI 都能联网或自动读取 llms.txt；本机 SDK 加载也不证明某个真实宿主已导入，更不证明真人通知送达。
