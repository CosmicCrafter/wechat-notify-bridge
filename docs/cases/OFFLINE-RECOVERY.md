# 工程案例：离线收件、租约和迟到结果

**工程案例 · protected 路径。** 一个接收器读到用户消息后离线，另一个接管；旧进程恢复后又报告完成。目标是保留消息、让接管可恢复，并阻止旧结果覆盖新处理状态，而不声称任意外部业务能恰好执行一次。

## 原方案的局限

单纯把“读取”记成完成会漏掉崩溃后的工作；只靠一个永不过期的领取记录，又可能永久卡住。事件回调还可能断线或过期，把它当唯一消息来源会遗漏离线区间。应用内成功记录也无法同远端业务事务自动原子提交。

legacy 的 generation=0 仍按旧合同工作；新租约没有被假装成所有旧客户端已经拥有的保证。

## 选择持久收件与可过期领取

沿用现有 SQLite、共享记录和单进程协调，不为这个规模引入新的消息队列。消息保存、读取、领取与报告各有状态，调用方维护游标和待处理输入。protected 领取加到期时间和代际，正常长工作续期，崩溃后允许新的 attempt 接管。

![旧代际迟到报告不能覆盖接管后的记录](../assets/inbox-lease.svg)

代际是服务端写屏障；租约也不是杀进程工具。接收器不能仅凭“租约到期”认定旧程序没有执行副作用。

## 实际实现与故障窗口

`storage/inbox_claims.py` 在事务中检查领取状态和代际。活租约下竞争只允许一个新的领取；过期后新请求递增 generation，旧 claim/绑定/代际不能续期或写结果。同一报告 ID 同内容可重放，不同内容冲突；终态不能降级。

| 故障时刻 | 能恢复的内容 | 调用方仍须做的事 |
|---|---|---|
| 读到消息但未落本地待处理记录 | 从原游标重新读取 | 按 inbox_id 去重，不提前丢弃游标区间 |
| 已领取但未执行即崩溃 | protected 租约到期后新 attempt 接管 | 核对原业务是否确实未发生 |
| 外部业务成功、报告前崩溃 | 消息和领取记录仍在 | 用业务幂等键/对账识别已完成副作用 |
| 旧进程晚到报告 | 服务拒绝过时代际 | 旧进程停止继续写；不省略 generation 绕过 |
| 订阅失效或离线 | 用持久收件箱补查 | 重新验证授权/绑定及必要订阅，不能只等新事件 |

归档不停止执行；结束监控需要结构化停止请求和匹配领取/代际的回执。即使回执匹配，也只能证明接收端作了停止陈述，真实进程状态还需运行环境证据。

## 如何验证与复现范围

`test_f02_leases.py` 用两次并发领取断言一个 200、一个 409，再在隔离数据库把租约置为过期，确认新领取进入下一代且旧报告失败。另一测试验证续期、错误代际拒绝以及一致备份重开后领取状态保持。它是可控时钟/副本测试，不是等同真实网络故障或大规模压测。

`test_f02_subscriptions.py` 验证订阅过期/取消后收件仍可补查；`test_f02_lifecycle.py` 验证离线停止不伪报成功。R3 的配套数据恢复经验强调保护升级后新增记录，而不是直接覆盖旧快照；本轮不接触生产备份。[证据与边界](EVIDENCE.md)说明哪些已执行、哪些没有。

## 已知限制

服务没有跨外部业务系统的分布式事务。failed 是应用报告的终态，不是自动重试队列。队列保留受磁盘、备份和运维影响；不承诺无限历史、灾难零丢失或所有宿主离线后自动唤醒。对性能或多 worker 扩容的结论需要另做测试，不能从单进程两请求竞争测试推导。
