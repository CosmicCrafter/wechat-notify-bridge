>
> 本文是 **F02 增量升级** 的交接依据，不替换 E0～E4 已完成的代码、管理端或先前产品方案。
>
> 生产稳定基线：`0bddeff` / `stable/2026-10-14-production-1.16.0`。升级候选已完成 E0～E4，随后提交共享会话组件 `81770be`。实际升级起点以当前隔离分支 HEAD 为准，先核实，不覆盖有效变更。

## 1. 一句话目标

**同一个接入应用使用一套长期身份凭据，能够动态创建多个独立会话；任何消息都只能投到明确指定的会话，只有经验证的对应接收端才能按其实际可证明的能力领取或执行；会话可独立结束，通知可按普通/紧急分流到不同飞书连接。**

服务仍然是统一消息中转站，不是内置 Agent、执行器、定时监控调度系统、多租户平台或复杂规则引擎。

## 2. 已确认的业务规则（不得反向改掉）

1. **身份与会话分离**：ChatGPT、Codex、Claude Code、业务服务器等各为接入应用；同一应用可管理多个不同会话（A01、A02、A03 是示例昵称，不是可信身份）。创建、暂停或结束一个临时会话，不重新申请应用 Key，也不影响其他会话。
2. **双方均可创建**：优先支持 AI 在实际工作上下文中注册并申请绑定会话；管理端可主动创建、先存首条消息，显示“待绑定 / 已入箱 / 待领取”的真实状态；不能随机转交给该应用的其他在线会话。
3. **准确路由**：会话 ID 必须稳定，改名不改变 ID；消息与任务在服务端绑定 `client_id + conversation_id`，不凭聊天标题、最近活跃会话或模糊文本推断归属。没有明确归属或绑定失效时保留/拒绝并说明，**不静默回退到别的会话**。
4. **单一主处理者**：默认每条会话仅有一个已确认的主领取/处理者。允许多只读观察者必须另有受控语义，不能因此重复执行。绑定、领取、完成及重复处理记录可追踪。
5. **归档≠停止**：归档仅整理列表，不停止通信、不撤销订阅；静音仅影响给本人的提醒；“结束监控”是向真正负责监控的外部程序请求停止，收到其确认后才显示“已停止”；若对方离线或未报告，则显示“停止请求待确认/状态未知”，不能伪称已经停止。桥本身不执行外部监控任务。
6. **通知目标独立**：同一个 ChatGPT 应用的日常通知可走飞书 A，紧急通知可走飞书 B；会话级偏好可覆盖应用默认，获授权的紧急规则可再覆盖偏好。未经授权不可随便走紧急连接，也不能承诺飞书 App 或操作系统一定发声。
7. **会话回复来源明确**：飞书/微信端回复具体消息或交互卡片，应按稳定平台消息关联映射回会话；无明确引用时不猜目标（尤其不能默认最近活跃会话），应引导选择或进入未归属消息队列。
8. **兼容**：保留现有 E0～E4、`81770be` 的管理端、手机端、MCP、HTTP、应用 Key、历史数据与旧客户端。必要的数据迁移应可验证、可恢复，旧行为的限制在迁移期明确展示，不能悄悄切断旧客户端。

## 3. 概念与职责边界

| 对象 | 解决的问题 | 权限与生命周期 |
| --- | --- | --- |
| 应用 Application | 谁在接入中转站 | 长期 `client_id`，一个或少量可轮换的应用凭据；一个应用下可有多个会话 |
| 会话 Conversation | 这件事是哪一段沟通 | 稳定内部 `conversation_id`、归属应用、显示名、归档/静音/监控状态 |
| 接收绑定 Receiver Binding | 这段会话应由哪个真实宿主上下文接收 | `binding_id`、宿主类型、已验证证据、能力、主处理者、状态与失效/换绑记录 |
| 收件与领取 Inbox/Claim | 消息持久保存、分发、认领、报告 | 稳定消息 ID、幂等、接收范围校验、领取租约与过期接管 |
| 通知路由 Routing | 应由哪个微信/飞书连接通知本人 | 应用默认、会话偏好、获授权的紧急级别；每个连接独立回执 |
| 外部监控 Executor | 谁真正执行抢票监控或服务器检查 | 始终位于中转站外；停监控、进度、完成/失败必须由它明确回报 |

### 重要安全事实：应用 Key **本身无法证明 GPT 聊天实例的身份**

当前实现按应用 Key 验证请求，`GET /api/inbox` 可以不指定会话，`inbox_claims.authorize()` 主要校验应用和连接授权；事件订阅虽按 `conversation_id` 过滤，却不意味着同一 Key 下的其他聊天无法请求该会话。

因此必须区分：
- **准确入箱**：服务端可以严格保证将消息写入某个确定的 `conversation_id`，不串到 A02。
- **强隔离领取**：只有宿主提供**可验证的接收上下文、可信的会话专属授权/绑定凭据或经验证的目标回调**时，才能进一步断言非 A01 不能读取或认领。应用主 Key 对所有会话普遍可见时，不能靠模型声明的 A01 文本或仅靠会话 ID 达成强隔离。

采用自动签发的限定会话访问能力时，必须核实宿主能否安全保存和提交该能力；不能因为“用户不用手工申请 Key”，就误称完全没有会话级凭据或绝对安全。**仅共享主 Key、无可验证宿主身份的场景应标为“应用级隔离/会话按 ID 过滤”，不能显示“已严格绑定”。** 必要时对受保护的新会话禁用应用级全量收件，按兼容计划渐进迁移旧客户端。

## 4. 会话创建、绑定与准确投递

### A. AI 主动创建（默认友好路径）

1. AI 以已有应用身份调用注册流程；使用稳定注册幂等键，生成/复用会话 ID。不得以会话名称作为唯一接收地址。
2. 按宿主能力走实际可验证的绑定：例如支持订阅的 ChatGPT Work 会话 / Dot，核验订阅过滤条件和回调挑战；其他宿主使用受控的会话接收能力或管理员配对确认。不能把有同一应用 Key 当成完成绑定。
3. 一个会话默认绑定一个主接收者；其他订阅可独立定义为观察者，不因存在多个订阅就触发多个业务执行。
4. 绑定变更或重新绑定必须有授权检查、旧绑定撤销、并发保护及审计；失效期间消息不允许错投。

### B. 管理端主动创建（已确认必须支持）

1. 管理员选择应用、会话名称、首条消息；服务端原子记录，稳定 `request_id` 防止重复创建及重复首发。
2. 如尚无可验证的具体接收上下文，状态为 **待绑定**；消息可先保存到明确的该会话收件箱，但不能冒称已经唤醒具体 GPT 聊天。
3. 对应执行端后续正确完成绑定，才能定向投递或领取；若无可用接收途径，页面应明确停留原因，不随机分发。

### C. 运行中收件

- 服务端验证当前 `client_id`、会话有效性、接收绑定权限及消息 ID，按精确目标入箱。
- 禁止无授权跨会话 `GET inbox`、`claim`、`report`、事件订阅（新严格绑定路径）；兼容旧接口须单列迁移路径，不在新安全状态下偷放行。
- 不能凭另一个会话正在在线、共享 Bot、同名或最后活动时间来转移执行消息。
- 事件推送是提醒，持久收件箱才是可补查的账本；回调 `2xx` 只能说明对方接收了 webhook，不能证明 AI 执行成功。
- 订阅过期/取消/宿主被删除时，应显示最后已验证时间与绑定失效状态，并支持重新绑定；**不自动启动离线聊天**。

### D. 领取与故障恢复

- 阅读消息、事件送达、**领取**、业务**执行结果**分成不同状态；只有显式确认才显示“已领取/处理中/已完成”。
- 在现有 `claim/report` 上定点增加可恢复租约/可续期语义（视实现选用），及递增 `generation/fencing token`，避免过期领取者后来覆盖新处理者结果。
- 领取超时允许受控重新领取、保留失败与转移审计；但执行端仍必须以消息 ID 做业务幂等，不承诺“任何情况下外部副作用恰好一次”。
- 重试沿用逻辑消息 ID 和请求幂等键；不因结果未知产生新消息、换目标会话或换 Bot 偷偷重发。

## 5. 生命周期的三个独立控制面

| 操作 | 会话历史/投递 | 对执行端的含义 |
| --- | --- | --- |
| 归档 / 取消归档 | 仅改变列表可见性，不撤销订阅、不停通信 | 不代表监控已停止 |
| 静音 / 取消静音 | 普通提醒暂停或按定义降级；消息仍留存，可查询 | 外部任务继续运行 |
| 请求结束监控 | 记录停止命令与接收状态 | 等待真实执行端报告“已停止”；超时仅报未确认 |
| 确认已结束 | 历史保留，后续外部消息按明确规则拒收或保存为异常，不伪报送达 | 执行端已确认停止，再结束相关绑定/订阅 |

迁移警戒：目前部分归档路由通过 `set_active(False)` 关闭会话并撤销事件订阅（例如 `api/admin_conversations.py`）；不要直接改一个前端按钮或重新解释旧字段。需先补独立的归档可见性与真正会话状态，审查历史记录迁移，保证不误恢复旧已停用会话。

## 6. 飞书 A/B 通知策略（先实现简单确定性规则）

- 最小方案：应用默认连接 A → 会话通知偏好 → **获授权的**消息紧急级别规则使用 B。
- 对旧客户端明确传入 `bot_id/channel` 的请求，保留原显式路由语义和授权验证；是否允许紧急级别覆盖显式选择需在实施中固定成可解释、不突变兼容性的规则，并写成测试。
- 一条逻辑消息允许多个有记录的投递尝试；发送结果分别记录，不把两个飞书投递复制为两个独立业务任务。
- 紧急路由必须有事先授权、限频/去重，不能让普通应用无约束持续触发 B；B 不可用时遵循已配置的明确失败/备用策略，不暗降级。
- 不保证飞书 B 在手机静音时一定鸣响；只能说明已选择哪个 Bot、平台是否接受、本人是否验证实际收到。
- 飞书/微信原生回复按 `reply_to`、原平台消息 ID 或卡片回调绑定消息/会话；无法证实关联时进入待归属状态。

## 7. 真实宿主能力边界（上线前逐宿主验证）

| 接入宿主 | 设计基线 |
| --- | --- |
| ChatGPT Work（MCP Events）/Dots | 根据已验证订阅与过滤条件发送事件；回调成功不是执行成功；不把回调视为通用安全会话身份。需要兼容订阅过期、Webhook 重试和不同步执行。 |
| 普通 ChatGPT 聊天 | 不默认声称支持任意定向后台唤醒；先确认当前运行形态有无可验证回调/接收能力。 |
| Codex / Claude Code | 能力取决于宿主与插件实际接入方式；有长驻接收器才按对应能力说明，离线时先可靠入箱，绝不承诺自启动。 |
| 服务器脚本与业务系统 | HTTP/MCP 可按 `conversation_id` 明确拉取/上报；业务副作用需要自己的幂等处理。 |

参考（2026-10-14 核验）：https://developers.openai.com/plugins/build/mcp-events —— ChatGPT 当前 MCP Events 面向 Work 聊天与 dots，提供带过滤条件的 webhook 订阅；回调 HTTP `2xx` 不是业务完成；对 ChatGPT 的该集成不支持 MCP Events 的轮询和 `gap`/`terminated` 控制通知，历史恢复需要中转站的独立收件账本与受支持的收件工具。

## 8. 实施顺序（每一批独立提交与验收）

### F02-0 合同与差异锁定

先定向检查 **最新版隔离代码** 中 `conversations`、`inbox_claims`、`mcp/events.py`、`admin_conversations.py`、现有通知发送/路由和实际宿主接入能力，不重做全量审计。交付最小数据/接口变更设计、旧客户端兼容表、失败与状态语义、针对目标宿主的能力矩阵。对 **无法实现强绑定** 的宿主明确标注限制，不以虚假成功充数；不因此中断其他可安全推进的工作。

### F02-1 准确路由与绑定

双方创建会话、配对/验证接收方、唯一主处理者、按绑定受控读/领/订阅、跨会话禁止错投、未归属飞书回复处理。迁移旧会话与旧鉴权采取受控兼容策略。

### F02-2 离线恢复与生命周期

持久入箱、显式领取/结果、领取超时与安全重新接管、旧领取者 fencing、订阅生命周期与补查、归档/静音/停止监控三分离。停止监控必须执行方回执。

### F02-3 通知分流

应用默认与会话偏好、获授权紧急路由飞书 B、限频/去重、失败处理、消息级别与显式目标兼容、回复归属和查询可视化。避免通用规则引擎。

## 10. 发布与授权边界

- 只在 `notify-bridge-upgrade` 当前隔离工作目录/升级分支实施；先确认工作树与有效提交，不覆盖 E0～E4 或 `81770be`。
- 不修改或重启生产服务，不修改生产数据库/密钥/平台 Bot，不合并 `main`，不自动进行真人通道验证。
- 每阶段需回归、浏览器关键场景、数据迁移和回滚检查，以及可供人工验收的本地入口；脚本/文档/导出包同步维护，避免旧说明污染。
- 对“宿主无法提供可信会话身份”“同 Key 无法证明实例来源”等客观限制，清楚报告可保证与不可保证的层级，**不为通过验收而绕过鉴权**。
- 任何必须扩大生产权限、改动旧语义或影响现有账号安全的事项，单独提出决策及推荐，相关部分停在安全边界，其余工作继续。
