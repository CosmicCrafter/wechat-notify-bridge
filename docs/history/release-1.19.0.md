## 部署前准入（生产操作须另获当次授权）

1. 核对最终 HEAD、源包 SHA、镜像及版本；对应提交的 Linux/Windows 托管 CI 必须通过，不借用旧 CI，不删除或关闭工作流。GitHub/Gitee 正式 main 和旧标签先只读比对。
2. 根据实际容器/Compose/挂载定位生产文件，不从仓库默认目录推测。保存旧镜像、原密钥、环境配置和运行用户清单，限制备份权限；不执行首次初始化覆盖已有账号、Key 或数据库。方法沿用[配置与数据保护](../server/CONFIGURATION.md#备份与恢复)。
3. 切换前复用现有 SQLite backup 取得最新一致副本，执行 integrity_check；热库不能只 cp 主文件。断网、无生产挂载/端口、禁用收发后台，实际检查恢复、解密、管理员、Bot/授权/历史/Key 与会话。合成数据演练不替代这项最新生产副本准入。
4. 前端构建、check_project、build_wheel、build_release/verify_release 后，按 server/Dockerfile 构建完整镜像。只切核实后的 Notify Bridge Compose 服务，保留原数据/密钥挂载、只读文件系统、10001 用户和单 worker；不启动第二个复用生产 Bot 的联网实例。

## 授权后的最小切换与验收

1. 记录窗口起点、旧镜像及回退点，只更新 Notify Bridge 镜像；不重建其他服务、删除卷、重新扫码或调整平台回调、权限、OAuth 配置。
2. 现有 Nginx /bridge/ proxy_pass 应覆盖 /bridge/docs/，优先不改网络配置。核对相对跳转、嵌套文章/图/JS/MD/OpenAPI/ZIP，以及 /wechat/ 和 .well-known 兼容入口。禁止将源码/admin/数据目录设为静态 root/alias。
3. 文档和管理动态响应沿用 no-store 和原 CSP，不添加 unsafe-inline/CDN，不让代理缓存覆盖应用头。必须检查公网实际响应，本机路径测试不能证明生产缓存配置。
4. 核实健康为 1.19.0、进程/镜像对应候选；管理员实际登录并查看历史/Bot/授权；原客户端验证身份、旧 API Key 与 MCP。先 dry_run，再在明确收件授权下做无害真实双向验证，平台接受/本人收件/归属/宿主唤醒分别记录。
5. 未登录访问公开 HTML、MD、OpenAPI、llms、Skill 和下载；管理数据、消息、Key、实例配置和含凭据导出必须拒绝。私密 ZIP 不进入匿名缓存。
6. 验收通过且正式发布获授权后，才快进合并 main、创建新版本/稳定标签并同步双远端和工件。旧 1.18.0 标签不移动；逐个 git ls-remote 核实正式提交一致，不强推历史。

## 失败时的恢复顺序

1. 停止新测试；先用一致备份保护升级后新增消息/状态及配套原密钥、配置，不直接用升级前快照覆盖。停止/切换接收进程仍在获授权的生产窗口内进行。
2. 本候选无 schema 变更。只有当次副本演练确认后，才用保留的 1.18.0 镜像、最新一致数据、原配置和密钥恢复，以保留窗口内消息。切回镜像本身不证明恢复成功。
3. 若旧版不能读取最新数据，保留现场并优先恢复；确需回到升级前匹配快照时，新增记录另行保全、核对和安排补回，不声称零丢失，不在未确认的数据上反复启动旧程序。
4. 恢复后核验 1.18.0 健康、管理员、历史、旧 Key/MCP、两平台通信与回调归属，确认无第二接收器或临时入口。耗时、消息影响和备份位置保存在私有发布记录，不公开原始密钥/路径。
