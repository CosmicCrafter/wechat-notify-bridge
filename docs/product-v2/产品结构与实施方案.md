# Notify Bridge 产品结构与实施方案

候选 v0.1 / 2026-10-14。本方案供产品结构与操作体验评审；未确认为正式需求，未改变业务实现。

## 定位与工作起点

Notify Bridge 是统一消息中转服务站。外部 Codex、Claude Code、服务器任务和业务程序通过 API/MCP 接入；站内负责通信平台连接、鉴权、路由、格式转换、收发与记录。Codex 可依据仓库资料在站外协助部署、维护及指导使用，不是站内 Agent。宿主接收器/事件订阅向外部调用方递交事件，不改变这个职责边界。

管理员的三个主要触发是：让新程序使用已有连接、连接一个新平台账号、根据失败通知定位原投递。导航与批次围绕这三个任务组织，不按密钥字段、接口数量或内部包目录组织。

## 四类对象及现有映射

| 产品对象 | 当前实现与关系 | 管理位置 / 边界 |
|---|---|---|
| 接入应用 | 复用 api_clients 调用方身份；Key 是认证凭据，不是独立应用。一个身份可有多个会话，一个身份当前只维护一把有效 Key | 接入应用：名称、启停、允许连接、默认连接、接入资料、密钥生命周期。AI/业务系统是资料选项，暂不新增强制持久分类 |
| 通信连接 | 复用 Bot 与 bot_id；平台是连接类型，一个连接对应独立微信账号或飞书应用和本人接收账号 | 通信连接：建立、绑定/配置、启停、测试。原平台能力与数据沿用，不自动更换身份或平台 |
| 投递规则 | 当前已有 Key 的 bot_ids/default_bot_id，加上请求显式 bot_id/channel 及权限检查 | 在接入应用中显示“允许连接与默认投递”，在详情保留原投递连接；本阶段不新增规则表、规则引擎、自动广播或备用路由 |
| 消息与回复 | 沿用 outgoing/channel_outgoing、inbox、chat_messages、会话与任务记录；按调用方、会话及 Bot 关联 | 消息：投递记录与回复两个视图。会话是组织上下文；任务卡片与答复是消息下的扩展，手机页保留其处理能力 |

省略 bot_id：使用应用默认连接；没有默认但只有一个授权连接时使用唯一连接；有多个候选时返回 bot_required。授权连接及默认连接不是凭据本身，配置文件中的路由偏好不赋予权限。改变默认连接不改变旧回执的原 bot_id；跨应用、跨连接去重边界保持。

## 候选导航

保留“总览、消息、接入应用、通信连接、设置与帮助”五项。暂不单列“投递规则”：当前规则很少，离开所属应用会增加寻找与配置成本。

| 导航 | 核心任务 / 主要内容 | 从旧界面迁入 |
|---|---|---|
| 总览 | 找到失败/未知投递，看到应用和连接数量，开始接入/建连接 | 新增只读摘要，复用既有状态；统计口径以实际查询范围为准，不假造送达率 |
| 消息 | 用应用、连接、去重键定位通知，核对状态、原因及关联回复 | 新管理入口。现有 caller-scoped /api/deliveries 和手机历史不足以直接支持管理员全局查询 |
| 接入应用 | 建立身份 → 授权 → 获取配置与使用资料 | “接入密钥”与“开发者文档”的配置导出向导合并；密钥操作保留在应用详情，避免列表堆积 |
| 通信连接 | 添加/配置平台连接，管理启停，核对收发与测试 | Bot 管理、二维码/飞书配置。绑定进度与投递结果分开显示 |
| 设置与帮助 | 按目的找部署/AI/业务系统资料，按需进入高级设置 | 代理设置、手机会话登录、其余参考文档。原手机会话页保持独立 |

原型展示主要流程。已有改名、密钥重置/停用/删除、Bot 删除、代理订阅/节点/检测、手机登录、图片/任务/草稿/归档等能力全部列为保留，不因未演示就移除。不可逆删除仍单独确认，密钥轮换明确旧凭据失效和外部调用方重配。

## 三条原型流程及隐藏规则

**接入应用：** 管理员为一个外部调用方输入符合现有规则的名称，选择资料使用方，授权通信连接并选择默认；核对后创建，直接获得配置/使用说明。无可用连接时先建连接，回来保留应用草稿。取消不创建，保存失败保留输入、不显示成功；已有应用允许零授权以暂停通信，新增向导以至少一个可用连接完成可用接入。空白默认值、唯一连接与多连接显式指定的语义分开。已有 Key 不回显；远程资料不携带 Key，本机/HTTP 私有配置由本人保存。原型下载仅演示 JSON/Markdown，不等同真实插件 ZIP。

**通信连接：** 管理员选择微信/飞书，配置/绑定本人账号；飞书回调与卡片回调使用该 Bot 的同一地址，完成平台发布；显式发一次测试，保留原连接与回执，再核对手机收件和回复。初次创建后保留“待配置”连接，取消后可从列表续接；发送失败和未知不是配置成功。原型保留已创建连接和已发测试记录；取消测试窗口不删除投递记录，完整配置后可返回应用授权。测试结果未知时禁用再次测试，先查原结果；具体人工再发权限需单独设计，不能换键绕去重。停用暂停后续调用和后台收发，历史保留。

**查询投递：** 管理员从总览进入失败/未知列表，按应用、连接、记录 ID 或原 dedup_key 查找，打开详情核对权限校验/平台阶段、错误分类和后续建议，查看关联回复或复制无正文排查信息。无数据、筛选无结果、读取失败分开。平台已接受不是手机已送达，无回复不是未送达；prepare failed 不硬判限额耗尽。旧记录缺诊断明确“无历史诊断”，不补造。

| 路径 | 谁做 / 需要什么 | 得到什么 / 后续验收 |
|---|---|---|
| 部署维护中转站 | 管理员/站外 Codex；源码、主机、HTTPS、运行目录、部署权限 | 复用 README、维护手册、配置模板、升级保护与恢复步骤；首次实例独立密钥/数据库，生产动作另授权；健康+登录+真实收发分别验收 |
| AI 接入中转站 | AI 宿主使用者；独立应用身份、授权连接、宿主支持能力 | MCP/插件或 stdio 配置、规则、安装说明；OAuth/私有 Key 配置+一次授权测试；无站内 Agent |
| 业务系统接入通知 | 后端开发者；应用身份、Key、允许连接、业务事件唯一标识 | HTTP/OpenAPI、轻量客户端示例、去重/回执/回复说明；重复事件、失败、未知、回复路由均验收 |

## 后续完整流程实施批次（本轮未执行）

| 批次 | 从真实触发到完整结果 | 影响范围 | 验收标准 |
|---|---|---|---|
| 1 应用接入交付 | 新调用方 → 名称/授权/默认连接 → 创建或选择已有身份 → 导出 → 调用方配置 → 一次通知及回执 | admin App/Keys/Developer/GrantsForm 合并；复用 client/grants/onboarding；generic/HTTP 资料定点补充；命名文档 | 独立新身份、无重复创建；原 Key/授权/会话不被重置；多连接/零默认正确；配置含私密内容显式标识；Codex/Claude/HTTP 各一种隔离接入实测 |
| 2 连接建立与验收 | 平台账号 → 配对或应用配置 → 发布/回调 → 显式测试 → 收件/回复证据 → 可供授权选择 | Bots/BotWizard，现有渠道设置/配对；必要管理员测试权限与诊断复用，可能最小增补记录；无长期测试服务 | 新/已有微信及飞书；重复账号拒绝；凭据留空保留；取消/失败可续接；测试原连接、结果未知不补发；本人真实收件/回复作为单独验收 |
| 3 通知排查闭环 | 总览异常 → 跨应用筛选 → 原回执/诊断 → 关联回复 → 下一步处置 | 管理员只读消息查询与前端列表/详情；已有存储定点复用；字段缺失兼容；查询分页性能 | 应用/连接隔离、不越权；接受/失败/未知不混；原去重键和 Bot 稳定；旧记录缺信息不伪造；筛选空态/查询失败；正文范围按用户确认 |
| 4 维护与帮助交付 | 部署者或用户选路径 → 找到资料 → 维护/接入/故障步骤 → 独立实例验证 | 现有文档/开发者资料包、代理及手机登录入口归位；补正文档冲突；不重写现有手机页 | 三条路径互不混用；秘密不进源码资料；从交付包干净解压可用；升级前一致备份/隔离恢复；生产上线必须另授权 |

每批均是可使用的完整流程，不先做完所有“列表”再做所有“接口”。生产回归覆盖关联面，改动保持局部；既有受保护功能先记录基线。设计确认后才详细核实各批 API/数据影响，不以原型 mock 字段冻结接口。各批在独立开发环境完成；上线计划另行提出。

## 需要决定的一个关键业务问题

1. **管理员是否可以查看消息/回复正文？** 建议默认仅状态、错误分类和定位信息；确需正文时提供明确的按需入口并限制记录。现有手机本人历史不等于管理端自动获得全局正文读取权限。原型中摘要/回复均是虚构，未据此决定生产权限。
现有授权、默认路由、未知结果不自动重发均继续沿用，不要求再次确认，也不在本轮引入补发/广播/备用连接。

其余技术与页面选择由实施者在已确认范围内处理，不要求逐字段确认。下一步仅接收产品结构、原型动线及上述正文访问范围的反馈。
