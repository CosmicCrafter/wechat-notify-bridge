# v0.3 管理与恢复

本候选实现只在隔离开发分支验收。正式服务仍采用用户给定 v1.16.0 / 0bddeff 基线；本轮不部署、不重启、不合并 main。具体稳定备份位置见升级工作区 AGENTS.md 中原保护说明；不将生产恢复副本联网用于开发。

## 日常管理

总览显示24小时异常与待处理任务；会话中心与手机端共享记录，管理员浏览不改变手机已读。接入应用是稳定身份，Key 是可轮换凭据；通信连接是微信/飞书 Bot。默认连接属于应用授权，不做失败后的跨平台自动改发。代理与节点位于系统设置，保持原订阅与回退机制。

会话中心与手机会话页共用气泡对话主体：应用消息在左，本人的回复在右，任务、图片与处理状态在同一时间线上。管理端提供应用筛选、新建与投递定位，手机入口提供本人登录和已读位置；两端身份与草稿独立。加载更早记录会保留当前阅读位置，发送后可以点击图片放大。刷新后尚未发送的附件保留ID，发送后再查看图片。

应用创建/Key轮换的原值只在签发时显示。旧 Key 末尾、签发时间未知时不推断。正常轮换默认过渡1小时（可0–24小时），更新各程序私有配置并验证，再主动结束旧Key。泄露时立即撤销具体Key，必要时停用整个应用；独立OAuth另行授权，停用应用同时禁止Key和OAuth。

## 账号迁移与恢复

管理端只接受管理员账号密码产生的独立Cookie会话，原管理员Key登录及重新启用入口已移除。老部署没有自动密码，必须在切换新版前用下述获授权服务器终端工具建立管理员账号（--initialize --username），确认密码登录和恢复路径。尚未建立账号时管理API返回admin_not_configured，不回退到Key登录，也不开放网页初始化。账号、手机Cookie和接入Key分离；应用API Key及OAuth接入保持兼容。

历史secrets/admin.json、admin-key.txt和数据库legacy_enabled字段可以保留作为旧版恢复材料，新版不读取它们进行鉴权；恢复历史数据库不会重新打开管理员Key登录。退回稳定v1.16.0时仍按该旧版本的认证及配套快照处理，这不是新版支持旧Key登录。

恢复绑定先发验证码到既有本人连接，收到后输入验证。找回页面只选择已绑定平台，不能临时改收件人。验证码5分钟、5次尝试，60秒间隔；普通历史/查询/日志中没有明文码。验证码请求返回不宣称手机收件，平台不可用时可用服务器兜底。

最后恢复连接不能在站内停用、删除或换本人身份。保持本人身份的Secret修复/重新扫码需当前管理密码，修复后原恢复证据失效，重新收到码验证前不视为可用恢复连接。外部平台仍可能故障，这个保护不保证永不失联。

## 获授权的服务器终端重置

只在获得该实例维护授权且有其数据库文件权限的交互终端执行。先确认实例与私有备份目录；不要把密码或Key作为命令参数。示例中的路径要替换为当前实例实际路径：

```sh
python -m wechat_bridge.admin_reset --database "<数据库绝对路径>" --backup-dir "<私有备份目录绝对路径>" --authorize RESET_ADMIN
```

首次安装尚无管理员时使用初始化模式；已有账号忘记密码时使用上方重置模式，保留原用户名：

```sh
python -m wechat_bridge.admin_reset --database "<数据库绝对路径>" --backup-dir "<私有备份目录绝对路径>" --authorize RESET_ADMIN --initialize --username "<管理员用户名>"
```

登录页未初始化时直接显示说明，找回密码页可展开“服务器终端恢复”，选择执行环境、填写路径并复制对应命令；网页不执行命令或新增公开初始化/重置接口。

- 本机入口默认数据库位于用户主目录的 .notify-bridge/data/wechat.sqlite3；--directory 自定义时为该目录下 data/wechat.sqlite3。
- ASGI 部署按实际 WECHAT_DATA/wechat.sqlite3 确认，使用安装服务的 Python 环境；不要新建空库替代正在使用的数据库。
- 仓库 Docker Compose 在 server/ 执行，服务名为 wechat-notifier，默认 ./.data 挂载到 /data。容器内数据库是 /data/wechat.sqlite3，持久私有备份目录可填 /data/admin-reset-backups；自定义挂载/服务名必须相应调整，勿写入只读 /run/secrets。

工具交互读两次新密码，先SQLite在线backup和integrity_check，再只改管理凭据与管理会话；不改通知/消息/应用Key/主加密密钥。没有公网无验证重置接口。终端快照生成和完整性检查不等于恢复测试。

## 升级与失败回退

上线必须另获授权，重新备份最新SQLite（一致性backup，不热复制写入中的单个文件）、配套原Fernet密钥、配置/部署镜像、客户端私有连接配置；记录代码commit/镜像/数据快照对应关系。沿用现有保护脚本与部署机制。

先在隔离、断网、无生产挂载、不启用通知/接收后台的环境恢复，检查数据库完整性，解密消息/图片/任务和Bot配置，校验旧/新Key与各身份。再做独立测试Bot、真人密码恢复、真实代理和新AI宿主验收。当前替身HTTP/UI证明不代替这些检查。

升级失败时：

1. 保存失败实例产生的新消息和最新一致快照，避免覆盖期间的新数据。
2. 根据保留的稳定commit/tag与镜像恢复匹配代码。
3. 恢复与该代码匹配的升级前数据库、原加密密钥、部署配置和客户端私有配置。
4. 隔离核验解密、身份、消息数量和权限后，获得正式恢复授权再启用正式服务。
5. 对失败期间新增记录另行评估迁移，不能直接把旧快照覆盖回去就宣称零数据丢失。

新凭据表有撤销/到期语义，旧二进制不读取它；不能只切旧代码接着使用升级后的库。也不能因回退重新启用已确认泄露的Key。没有数据/配置匹配与恢复证据时先保留实例并停止受影响操作。

仓库根目录以独立环境运行 scripts/run_v03_test.py，访问 [本地管理端](http://127.0.0.1:19865/admin/)；随机账号仅在 .private/test-v03/local-access.json。此目录与生产完全独立，所有平台/扫码/代理出口都是替身，长期收件/定时后台关闭。页面有明确测试标识；真人验证码接收须独立测试Bot。

scripts/verify_v03_test.py 验证HTTP流程；scripts/verify_v03_mcp.py 验证新应用通过真实stdio MCP SDK发现/调用工具并与管理端、手机HTTP共用账本。它们不连接生产、不证明真人平台或新Codex/Claude宿主已安装成功。


## 连接配置的三种状态（F03/F04）

新建记录先为“待配置、不可投递”，不自动启用；关闭向导后从该记录“继续配置”，不另建同名连接。飞书向导显式验证 App ID/Secret，通过后原子保存加密配置并按开关启用。失败时保留表单，显示验证拒绝代码、网络不可用或响应异常，原配置/授权不改。保存仅证明凭据落库，不证明消息发送、本人回程或回调权限可用，需另做既有收发测试。

旧保存 API 未传 verify_credentials 时维持原本地配置校验合同，不新增隐式平台请求；新向导明确传 true。旧已保存记录与授权不批量迁移。微信新连接允许先扫码，成功首次绑定后启用；已有停用连接不会因凭据修复自动启用。真实收发证据仍来自既有连接测试。

向导底部保留必要的上一步、保存并继续和完成，关闭使用右上角×。未保存输入关闭需确认，已创建待配置记录保留；正在扫码时关闭会取消本次扫码。提交期间锁定操作并防双击跨步，取消关闭继续保留现场。真实账号密码、Bot Secret不放入报告或日志。
