## 1. 核心对象与关系——以后新需求先找归属

| 对象 | 用户理解 | 当前代码的主要对应 | 设计规则 |
|---|---|---|---|
| 接入应用（Application） | 哪个 AI 或业务系统在使用中转站 | `api_clients`、客户端授权 | 身份 ID 稳定；改名、换 Key 不改变会话归属 |
| 应用凭据（Credential） | 接入应用的 Key/OAuth 凭据 | 当前每应用一个 `key_hash` | **凭据不是应用**；新版本可以准备独立 Key ID 和可控轮换生命周期 |
| 通信连接（Connection） | 中转站连接的一个微信/飞书 Bot | `bots`/`bot_id`、渠道配置 | 一个连接独立配置；是否已配置、能收、能发、能互动分别证明 |
| 投递偏好（Routing） | 该应用默认通过哪条连接提醒我 | 已有 `bot_ids/default_bot_id`、请求显式指定 | 权限检查先于路由；无权目标不可因规则被放行；首版不需要独立规则引擎 |
| 逻辑消息（Message） | 谁说了什么、要表达什么 | `chat_messages`、`inbox`、原消息 API | 一条消息有稳定 ID；支持普通通知、结果、交互任务的统一语义 |
| 投递尝试（Delivery） | 这条消息对某个连接实际发得怎么样 | `outgoing`、`channel_outgoing`、诊断 | **一条消息可有多条投递记录**；接受不等于本人读到 |
| 会话（Conversation） | 围绕一个应用的持续沟通 | `conversations`、`chat_messages` | 归属以 `client_id` 和稳定 ID 为准；管理端与手机端共用账本 |
| 任务及回复（Interaction） | 需要本人决定的消息及其答复 | `task_cards`、`inbox`、回复历史 | 一项任务只有一份有效决定；桥只报告通信事实，不代业务执行 |

**关键关系：**一个应用可有多个会话；一个会话可有多条消息；一条逻辑消息可对应多次有记录的投递；一项交互只能产生一个有效答复。连接的默认值发生变化，不改写历史消息的原连接。平台原生消息未经过桥、或旧记录未保存正文时，不声称有完整历史。

**导航状态：**从任意总览卡、应用详情、连接详情进入投递记录或会话中心时保留查询条件；从某条投递记录返回关联消息时定位到**具体消息**。找不到真实关联时明确提示，不猜关系。管理端窄屏使用抽屉导航；原手机 `/chat/` 保留适合手机的独立会话体验，不机械移植整个后台。

## 3. 各页面详细体验准则

### 3.1 总览：按成熟度显示，而不是长期摆“快速开始”

- **新实例**：还没有有效应用或连接时，显示短接入向导，完成后自动退出主视觉区；始终可在帮助中重新打开。
- **日常使用**：首先显示“需要处理”的失败/结果未知/待本人答复；其次是最近重要活动与相关连接故障。正常时可简洁显示“当前无待处理问题”，不要用四块大数字卡充满视野。
- 状态必须有可解释口径和时间范围，点数字跳到有对应筛选的真实记录。`/health` 仅代表进程响应，不能被写成微信/飞书全部可达。
- 区分**故障**与**值得了解的事件**。不要把每次心跳、请求计数当作大红色告警。

### 3.2 会话中心：已确认的 A 方案 + 主动新建

**布局：**桌面左侧会话列表和搜索、中间时间线及消息输入、右侧按需展开详情；窄屏单栏。首屏重点是会话对象、最后内容、待答复、实际接收状态，不是字段说明。

**新建会话的首版完整动线：**

1. 管理员点击“新建会话”，选择**已登记、未被停用且有有效收件途径的接入应用**（例如 Codex、备份系统）；展示应用名称、稳定标识、最后活动时间和可验证的收件方式。**不得假设 Codex 在线。**
2. 可选填写名称并编写首条消息；草稿阶段不创建空会话。点击发送后由服务端以稳定幂等键**一次性落下会话、首条消息与收件记录**。重复点击或同键网络重试返回原结果；同键不同内容报冲突。
3. 进入同一会话时间线；手机 `/chat/` 也能看到该会话。后续回复沿用同一会话 ID、收件箱、历史与权限规则，不增加管理端专用聊天数据库。
4. 能收件但客户端离线时：写成“**中转站已保存，等待客户端领取**”；不能收件时：阻止伪发送并明确原因。只读过收件箱不等于实际处理；需要**客户端显式领取确认**才能展示“已领取”。如果当前协议没有该确认，就仅显示已有证据。
5. 后续由应用报告处理中、完成或失败时，可在会话中展示；无法证实时保留“未报告”。不承诺启动离线进程或恢复 Codex 原先宿主聊天窗口。

**已有会话与任务：**可直接回复文字、按原能力发送图片、查看历史与任务卡片；普通回复和任务答复控件分开。任务提交应保留既有输入类型、一次有效决定、幂等与冲突规则；手机和管理端同时答复只能有一份有效结果。已关闭、被撤权、已归档或已删除的会话不可假装能继续发送。

**记录真实性：**只显示通知桥实际保存并关联的消息；未关联入站单独呈现“未归属”。时间线标识原生微信/飞书、手机页、管理端等来源。管理员浏览**不改变**原手机 `web_reads` 进度，也不改变客户端已领取/执行状态。管理员自己的未读若没有可靠独立状态，首版可以不显示，优先给“待本人答复数”。

**操作后果：**置顶、改名、归档、删除都要明确对手机端、收件与任务的影响；优先提供归档，永久删除需要明确警告，不能把删除说成“仅从列表隐藏”。长会话要有分页、向上加载、消息锚点、稳定返回现场；图片/附件的访问继续受身份鉴权保护。

### 3.3 投递记录：排障入口，不是第二个聊天窗口

主要筛选：应用、通信连接、时间范围、状态、会话、消息 ID／去重键。每条记录明确原始请求、目标连接、不同投递尝试和可用诊断；支持复制**不包含秘密**的排障摘要。

投递状态不得用一个“成功”表达所有事实：请求已保存、投递尚未开始、平台明确拒绝、投递结果未知、平台已接受、本人收件确认、客户端领取、业务完成分别由对应证据决定；旧记录缺诊断就显示“历史信息不足”。从会话跳详情，再原路返回定位原消息。

### 3.4 接入应用：把“Key”还原成应用的一项凭据

应用列表展示名称、稳定 ID、允许连接/默认连接、启停、最近调用和关键异常；主要操作是“查看接入配置”，低频高风险动作在详情。创建应用流程：填写应用名称→选择允许连接/默认连接→创建身份→一次展示新 Key→选择导出 AI 或系统接入资料→受控验证。Codex / Claude Code / HTTP 是**本次导出类型**，不是永久绑定的应用身份类型。

- **新 Key 方案建议**：新发凭据采用识别度高的 `nb_` 前缀和高熵随机部分；同时提供**非秘密的公开 Key ID**，明确对应哪个应用。前缀不能替代授权，也不必在密钥内编码应用名称；历史 Key 继续兼容。
- **复制规则建议**：创建或轮换时一次完整显示并提供复制；日常展示 Key ID、掩码末尾、状态、创建/轮换/最后使用时间，**不从哈希存储反推出旧 Key**。用户丢失密钥走新 Key 轮换，而非无限回显旧明文。
- **正常轮换**：设计受控的新旧凭据短暂并存和结束迁移；**泄露撤销**：立即禁用受影响凭据并提示正在依赖它的系统。现行 1.16.0 单哈希、即时旋转不能假装已支持并存；需单独设计迁移与权限验证。
- 更换 Key 不改变应用或既有会话 ID；修改授权会影响后续请求，但不抹去历史记录。删除应用前展示相关会话、收件箱和既有接入方影响。

### 3.5 通信连接：重心在“配置和验证”，不是字段清单

一个连接代表一个可用的具体微信/飞书 Bot。列表显示配置状态、最近认证/发送结果、最近入站、回复是否支持与人工确认；这些是**分立事实**。新建采用已有向导续办：创建待配置对象→平台配置/配对→回调或能力检查→发送测试→本人收件或回复验证→开放授权。失败可从原步骤继续，测试不能悄悄生成重复消息或更换去重键。

停用、删除、重绑前展示受影响的应用、默认连接和恢复绑定。**最后一个已验证的管理员恢复连接，不允许被站内流程直接停用、删除或替换身份；先验证新的恢复连接，再解除旧保护。** 平台外部故障仍可能发生，所以保留服务器兜底，不宣称此保护能保证永不失联。

### 3.6 账号与安全：全部在右上角头像

单管理员模式优先，不扩成多用户权限平台。账号密码登录、修改用户名与旧密码改密，使用安全密码哈希和受保护会话；改密或恢复成功后撤销旧管理会话，**不影响接入应用 Key、通信连接和数据加密主密钥**。

忘记密码时只发送到**预先绑定并成功验证的管理员本人微信/飞书**，不允许在找回页面临时指定新的收件人。验证码短时有效、一次性、限速、限尝试，验证码本身不进入普通聊天历史、API 查询或日志。换绑必须验证新身份才解除旧绑定；若完全失去恢复途径，通过**经授权的服务器终端重置工具**只修改管理凭据与会话状态、保持所有消息和加密资料。

现行生产仍使用管理员 Key；迁移到密码登录时要有受控的首次初始化、灰度验证及旧入口撤销步骤，不能发布 v0.2 原型中的示例密码或验证码。管理员会话与手机 `/chat/` Cookie、业务应用 API Key **身份隔离**，防 CSRF、重放和越权。

### 3.7 系统设置中的代理/节点：现有功能归位和精修

顶部只突出**当前生效出口、模式、最近检查结果**；节点搜索、固定候选、订阅更新和高级设置下沉。必须清楚区分“选中草稿”与“实际已应用”。手动模式失败不得暗换节点；自动模式按已有优先组规则回退。订阅、检测、应用失败保留旧配置；旧配置也无法确认时显示“生效状态未知”，不能虚报成功，也不能为求畅通而擅自改成直连。订阅私密字段留空意味着保留，不在列表或日志中回显。

### 3.8 全局视觉与操作体验

中等信息密度，统一字号级别、标题层次、表单、主次按钮、危险操作位置、抽屉/弹窗、状态色与提示；不依赖大量浅色小字或长期占屏的说明卡。列表保留适当横向滚动，窄屏使用分层详情。模拟原型必须覆盖空态、失败、加载中、取消、部分成功、结果未知、表单校验、未保存离开、返回原筛选和历史定位。至少验收约 1440px 桌面和 390px 手机视口，并检查键盘焦点、可读对比度和关键文本可访问性。

**原型交付质量门槛：**上传的 v0.2 原型 ZIP 主要包含构建后的 `app.js`、`style.css`、截图和说明，**没有随包给出可维护的 Vue 组件源码与构建脚本**。下一版应交付完整可编辑原型源码、运行/构建说明和可直接打开的离线预览，禁止后续 AI 只能不断修补巨大构建产物；“Windows 双击可用”必须实际测试后才能声称通过。

## 4. 三条对外交付路径——文档也是产品

| 路径 | 入口与内容 | 独立验收 |
|---|---|---|
| **维护/部署自己的站** | 仓库 README → 简短 AI 工作入口（可引用 AGENTS.md/CLAUDE.md）→ 维护手册、环境/部署、升级与恢复，版本一致 | 新 Codex 在隔离测试实例中读懂源码、按现行方式部署/升级，不碰用户生产资料 |
| **让另一个 AI 与手机通信** | 应用授权 → AI 接入包（MCP/stdio 或适用的远程方式、Skill/使用说明、版本/能力声明、验收步骤）→ 宿主安装 | 新 Codex 和 Claude Code 分别按其真实宿主配置完成发送、收件、回复验证；明确自动唤醒是否真的支持 |
| **让业务系统使用通知** | 应用授权 → HTTP/OpenAPI 接入包、示例代码、幂等与错误说明、回执查询 → 系统集成 | 简单脚本/服务发送通知、同键防重、查状态；不装 MCP，不依赖 AI 运行时 |

规范文档维护一份有效事实源，其他使用手册按角色引用，历史文档留在历史区。接入包按用途筛选内容，**不能把全部 Markdown 不分场景塞给每个客户端**；客户端包写明目标、版本、入口、所需权限及“从这里开始”。含真实 Key 的**私密配置包**与可直接提供给 AI 阅读的说明包清楚分离；普通包不包含平台 Secret、服务器 SSH、管理员凭据。网页和 Codex 配置助手最终调用同一管理服务，不能各自维护独立配置逻辑。

## 5. 由原 46 项候选问题收束的 12 个工作包

> 原 46 项是排查维度，不是 46 个要新增的功能。下表用可交付、可验收的工作包替代重复的“逐点优化”任务。

| 编号 | 工作包 | 完成内容 | 主要性质 | 优先级 |
|---|---|---|---|---|
| W01 | 信息架构与通用 UI | 导航、右上角账号/帮助、统一组件与响应式、返回现场 | 原型和前端重组 | **P0** |
| W02 | 总览与状态口径 | 新人/老用户差异、待办/异常、统计含义、真实健康证据 | 前端 + 少量聚合查询 | **P0** |
| W03 | 会话中心 A + 新建 | 读、创建、发首条、回复、任务、跨端一致、未读隔离 | 复用旧聊天 + 新管理员接口/约束 | **P0** |
| W04 | 投递排障 | 管理员跨应用查询、诊断、去重/阶段、会话精确跳转 | 新只读能力 + 前端 | **P0** |
| W05 | 应用/接入 | 应用身份归位、授权、默认路由、导出向导 | 复用 CRUD/onboarding，调整流程 | **P0** |
| W06 | 凭据生命周期 | Key ID、`nb_` 新 Key、一次复制、正常轮换、紧急撤销 | 数据/鉴权升级 + UI | **P0** |
| W07 | 通信连接 | 配置与验证分层、受影响应用、恢复连接保护 | 复用 Bot/渠道，补影响校验 | **P0** |
| W08 | 管理账号与恢复 | 登录、改名、旧密码改密、验证码绑定/找回、服务器兜底 | 新认证 + 受控迁移 | **P0** |
| W09 | 代理和节点 | 当前/候选、生效/回退、订阅/节点分层 | 主要是原有功能体验整理 | **P1** |
| W10 | 可靠性和统一状态 | 已知 R1–R3、任务结果/领取边界、危险操作保护 | 定点后端修复与回归 | **P0 门禁** |
| W11 | 三类 AI/系统交付 | 有效文档入口、按角色导出、干净环境上手、密钥隔离 | 资料/脚本/安装验证 | **P1（本轮范围）** |
| W12 | 消息丰富性 | 普通通知/进展结果/交互三类排版语义与能力降级；先预留设计 | 可先原型，复杂格式编辑器后续 | **P2** |

**P0** 表示本轮正式升级不可缺少的能力或发布门槛；**P1** 表示本轮应完善但能独立验收的体验与交付；**P2** 表示可做设计预留、正式扩展另排批次，不应阻挡核心上线。安全、权限和兼容校验不因分级而豁免。

## 6. 分批实施顺序与停止点

| 批次 | 完整用户场景／交付 | 依赖与验收 | 生产边界 |
|---|---|---|---|
| **D0 统一原型** | 基于本方案一次性完成总览、会话新建/回复/任务、投递、应用 Key、连接、账号、代理的 **v0.3 可交互原型** | 提供**原型源码+离线预览**；视觉/窄屏/异常/取消全路径验证；用户一次集中反馈 | **仅设计，不改正式后端/生产** |
| **E0 工程门禁** | 当前升级分支上定点复核 R1–R3、定义原 API/存储兼容和安全迁移边界 | 回归测试先于并发/去重调整；保证旧数据能读、旧凭据不突然失效 | 不重跑全量历史，不更换技术栈 |
| **E1 管理身份底座** | 受控管理员密码认证、独立管理会话与全局查询读权限，兼容当前管理员 Key 的迁移 | 防暴力尝试、Cookie/CSRF、权限隔离、迁移和恢复方案在隔离实例验证 | 没有验证不切换生产登录 |
| **E2 核心中转闭环** | 新接入应用→授权→发送→投递诊断→管理端新建会话/回复/任务→手机共享→应用收件/报告处理 | 原会话索引与收件箱复用；首条消息原子幂等；两端任务争用、离线领取、旧记录、故障回归 | 完成一个完整场景再扩展下一场景 |
| **E3 配置与安全闭环** | 连接新增/测试/授权→Key 正常轮换或泄露撤销→管理员恢复通道与服务器兜底→代理现有操作精修 | 回复能力验证、连接删改影响范围、最新备份、敏感操作审计与恢复演练 | 服务器工具不得成为公网绕过入口 |
| **E4 三条路径交付** | 维护者资料、Codex/Claude 接入包、HTTP 业务包；配置助手复用管理服务 | 新会话/干净环境安装及端到端测试；敏感文件扫描；与服务器发布版本一致 | 不把私密安装包推到代码仓库 |
| **E5 后续扩展** | 消息模板与渠道预览、更多通道、有限通知策略 | 在统一消息语义和通道能力声明之上另立项 | 不抢占 v0.3 核心修复与交付 |

**每批完成标准：**一条端到端操作流程能正常工作，附清楚的 API/权限/数据影响范围和自动测试，不仅是页面截图。任何改动越过已确认产品边界、会破坏稳定 Key/旧 API/历史数据、涉及生产部署或敏感迁移时，先提出少量带影响与建议的决策项；不要求用户逐字段审批。

## 7. 必须覆盖的验收场景（设计阶段先写清，不代表已实测）

| 编号 | 验收场景 | 正确的可见结果与不变量 |
|---|---|---|
| T01 | 全新实例与已运行一年实例分别打开总览 | 仅初始阶段重点显示快速开始；老用户不被向导占屏；指标可下钻 |
| T02 | 用接入应用向导配置 Codex、Claude、HTTP 三种资料 | 是同一应用的不同导出用途；不发生多余的应用创建或自动 Key 轮换 |
| T03 | Key 首次创建、遗失、常规迁移、确认泄露 | 明文仅签发时提供；正常轮换受控过渡，泄露立即撤销；旧 Key 兼容直至迁移决策 |
| T04 | 新增微信/飞书连接，执行测试收发 | 明确区分已保存、已配置、平台接受、本人收到、可以回复；失败能续办 |
| T05 | 关闭或删除一个连接 | 准确列出受影响应用和默认路由；恢复绑定中的最后有效连接受保护 |
| T06 | 管理员主动新建会话并发送首条消息 | 同一应用下生成一条稳定会话、一条有效首消息；手机端可见 |
| T07 | 新建会话重复点击、超时、恢复页面重试 | 不产生重复空会话/首条消息；原键可查结果，同键不同内容冲突 |
| T08 | 目标 Codex/Claude 离线或从未安装收件组件 | 收件能力不存在则拒绝虚发；可排队则显示待领取，不宣称唤醒或处理 |
| T09 | 手机与管理端同时答复同一任务 | 只有一份有效决定；另一方看到已处理/冲突，不能改写第一次决定 |
| T10 | 管理端查历史、删除/归档、图片访问 | 查历史不清手机未读；删除影响说明真实；所有下载有身份校验 |
| T11 | 会话消息↔投递详情↔返回原位 | 正确定位记录与原会话；筛选/滚动/锚点保持；未关联不乱连 |
| T12 | 微信发送外部响应长时间阻塞 | 手机答复及不相关操作不被整段网络等待占住，同时去重保护不失效 |
| T13 | 飞书令牌阶段失败、发送后结果未知 | 投递前可受控恢复，发送后未知仍先查结果、不盲重发 |
| T14 | 手机任务已答，飞书卡片同步失败 | 已保存答复不被倒写成失败；飞书显示同步状态且可按规则恢复 |
| T15 | 管理员输入错密、改密、忘记密码、换绑与服务器兜底 | 验证失败不改资料；验证码不进聊天与日志；旧会话撤销，消息/主密钥/应用 Key 保留 |
| T16 | 代理手动切换失败、自动优先组回退、订阅失败 | 旧有效配置保留或状态明确未知；草稿不冒充生效；不擅自降级直连 |
| T17 | 390px 手机、1440px 桌面、离线打开原型 | 抽屉导航与可点击流程可用；真实验证才能报告“已通过” |
| T18 | 新 AI 只拿交付包，不知道项目背景 | 能明确选三条接入路径、取得正确权限/版本资料；不接触无关敏感信息 |
| T19 | 旧版消息、旧 Key、旧登录与数据库迁移 | 不能凭 UI 改名破坏旧合同；迁移可核查、恢复计划包含最新数据保护 |
| T20 | 线上升级前的完整验收 | 当前最新数据一致备份、隔离恢复，真实管理员登录与微信/飞书收发通过后才请求部署授权 |

## 8. 主要风险与防护手段

1. **认证切换锁死本人**：密码体系必须有可验真的初始设置、恢复绑定/换绑和服务器兜底；避免“为了新安全特性把自己关在门外”。
2. **密钥生命周期改变旧接入**：1.16.0 仍是单 Key 哈希/即时旋转，新增重叠轮换前先设迁移边界；`nb_` 前缀与新公开 ID 不能反向破坏已有 40 位数字 Key。
3. **管理员新会话未找到客户端**：存到统一应用收件箱并准确区分等待领取；是否主动唤醒由宿主已有接入能力决定，不升级为无授权远程执行。
4. **重复与状态混淆**：会话创建/首消息、任务答复、平台投递均有独立的幂等边界；平台成功不能冒充业务已完成。
5. **“完整聊天”误扩大权限或误导历史**：仅展示已经保存的会话历史；管理员写操作、附件下载、防 XSS、归档删除都需受控；不伪造外部聊天平台历史。
6. **界面改动演变成全面重构**：利用已有 `api_clients`、`conversations`、`chat_messages`、`inbox`、`task_cards`、渠道驱动和前端组件，定点迁移而不是重造系统。
7. **资料包泄露秘密或文档互相矛盾**：说明包/含密钥的私密包分离；有效规则只有一个权威来源；完整资料仍在仓库，但接入包按场景精简。
8. **生产回滚丢失新消息**：稳定保护只覆盖原冻结时点；每次上线前都要重新备份最新数据，回滚前先保留失败实例中新产生的数据。源码备份不能代替一致数据库+原密钥+镜像的恢复链。
9. **原型看着“可运行”却不可维护**：可编辑源码、构建脚本、原型测试记录和静态预览一起交付；不把压缩后的演示 JS 当下一阶段唯一维护源。

## 9. 后续 Codex 执行的共同规则（本轮**不发送执行命令**）

- 先使用现有源码、已形成的审查报告、v0.2 原型与本收口方案；**不得反复全量审计历史，不因漂亮 UI 重做后端**。
- **设计一次集中验收、开发分批交付**：D0 把完整原型一次整理到位；E0–E4 按端到端场景实施，避免同时大动登录、路由、存储和移动端。
- 每批交付应回答：这个场景现在怎样使用、改动了哪些现有模块、旧行为是否兼容、关键回归结果、未验证的外部依赖和下一步风险。
- AI/脚本不得把普通客户端 Key 当管理员、不得把聊天文本当自动执行授权、不得默认回显原始凭据、不得在生产发真实测试通知而未经允许。
- 如果事实依据冲突、设计规则无法覆盖或存在不可逆迁移，暂停受影响部分、列出方案和影响；其余独立工作继续。
- 生产版本、数据和两远端保护保持；新的生产部署及线上密钥/数据库迁移必须另行授权。

## 10. 收口时的“冻结项”和下一次审阅重点

**可以直接冻结的产品共识：**定位、四大核心对象与会话关系、三条交付路径、管理端会话中心 A+主动新建、旧手机会话继续存在、记录真实性、站外 Codex 角色、管理账号及安全恢复目标、稳定生产隔离原则。

**建议作为 v0.3 原型的一次集中审阅重点：**总览的日常密度；会话新建与离线提示；应用 Key 轮换的用户文案；通信连接测试与影响确认；账号恢复的入口；代理当前/候选区别；桌面与窄屏一致性。这些先通过一个统一原型确认，不必再逐字段问业务决策者。

**尚需技术验证、不能以原型代替实测：**客户端收件确认协议、管理员密码迁移、正常密钥重叠轮换、最后恢复通道后端保护、全局投递查询、浏览器 file:// 离线兼容、真实跨端同步与平台测试。

**设计停止点：**本文件是“可进入 v0.3 统一原型设计的一次性工作依据”，**不是已经验收完成的新版产品，也不是授权重构/上线**。下一步是按照 D0 生成可维护、可交互的新原型并让用户集中试用；确认后才逐批开发真实服务。
