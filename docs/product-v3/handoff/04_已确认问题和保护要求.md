## 1. 定位和边界

Notify Bridge 是**统一消息中转服务站**，不成为业务任务平台或内部 Agent。外部程序、Codex、Claude Code 通过 API/MCP 接入；平台连接统一集中在中转站；中转站负责授权、路由、收发、格式适配、回复关联、记录和诊断。Codex 作为外部维护、部署、接入和使用教学助手。稳定基线和生产备份保持独立。

“需求一次考虑完整”不等于“代码一口气重写完”；建议先确认本清单，原型整体验证，再按可回退、可验收的完整流程分批实现。

## 3. 会话中心：建议正式加入

### 必须保留的既有能力

- 从原 `/chat/` 复用会话列表、搜索、置顶、归档/恢复、删除、历史分页、未读、图片、Markdown、任务卡片及双向回复能力（存在能力不等于立刻全部在管理端另做一份）。
- 管理端用桌面友好的“左侧会话列表 + 中间消息时间线 + 按需右侧详情”，窄屏转单栏；不保留常驻大幅说明书。
- 左侧可按接入应用筛选；每行显示名称、来源应用、最后时间、最后摘要、未读/待办。右侧消息显示发送者、方向、精确时间、关联连接、消息状态；未配置或失败明确区分。
- 点击一条会话内通知可查看技术投递详情；在投递记录点“查看会话”可跳到准确的消息锚点；无关联会话显示“未建立会话”，不生成假会话。
- 原手机 `/chat/` 仍保留，手机端不强行迁移到管理页面，也不共享不必要的设置导航。

### 真实数据的范围与安全约束

- “完整记录”严格指**已经经过通知桥且实际保存、关联到会话的内容**；不能自动读取宿主/飞书/微信内未经过桥的历史；旧版仅保存哈希的正文无法补回；删除的记录不得被恢复成可见内容。
- 入站但未关联到某个会话的消息，可另外标注“未归属/公共收件”，不猜测对应应用，不将其伪装为某个会话的一部分。
- 管理员浏览会话 **不能自动更新手机端的 `web_reads` 阅读位置**，也不能把“管理员读了”写成“外部 AI 已领取/执行”。如果要给管理端未读数，应独立统计。
- 管理端使用**管理员认证权限**访问记录和进行回复/任务操作，不能拿应用 Key 冒充全局权限，不能把手机一次性登录码转成管理员凭据；图片及附件下载同样需要保护。
- **已确认管理端可回复和处理任务**：写操作必须复用原 `request_id` 去重、会话状态检查和回复路由；结果未知时按原 ID 查询/恢复，不能换新 ID 盲目再提交。
- 会话搜索、分页、长文本/Markdown 的 XSS 防护、附件权限、删除确认、备份保留范围需要同步设计。

### 已确认决定 A：管理员可查看、回复和处理任务

**确认来源：**用户在本轮明确选择“管理端会话中心 A：能够查看完整已记录会话，也能够直接回复消息、处理任务”。不再把只读方案作为平行备选，也不重复提问。这里的“完整”仅指通知桥确实保存且能够关联的记录，不能从微信、飞书或 AI 宿主拉取未经过桥的全部聊天历史。

**工作范围与交互规则（候选实现细则）：**

1. 管理端支持浏览历史、搜索、精确跳转、对已有且可写会话发送普通回复；任务卡片支持沿用现有 single/multiple/confirm/input/form 模式，按同一数据合同处理。普通回复和任务答复是不同操作，不能“输入一句话”隐式执行任务。
2. **首版正式支持“主动新建会话”**：管理员可选择已授权的接入应用，填写可选标题和首条消息；新会话创建及首条消息须有明确幂等语义，且与回复已有会话共用收件箱、历史账本和权限检查。具体规则见下一节。
3. 管理端和手机端提交同一任务：服务端只能记录**一份有效决定**。相同决定重复提交按原结果返回；不同决定冲突时提醒“已由另一端处理”，展示有效决定，不覆盖旧结果。过期、取消、已结束、已归档和应用被撤权时不能继续交互。
4. 普通消息保存、送达中转站、AI 客户端已领取、任务实际处理，是不同状态。发送成功不能写“Codex 已执行”；若应用失联、客户端停用、会话归档，要及时提示“暂不能投递/仅保留历史”，不能仍显示一个看似可用的发送按钮。
5. 管理端浏览历史**不改变手机端已读指针**，也不更新客户端收件/执行状态。若需要管理端未读数，单独记录管理端阅读位置；初版也可以只展示“待我处理数”，不抢着建第二套未读体系。
6. 管理端回复与手机回复使用同一会话、相同消息账本与路由，但记录操作来源（管理端/手机端）；两端刷新后看到同一条真实消息，不能双份插入，不能把管理操作冒充微信原生回复。
7. 回复前显示目标：应用、会话、实际关联的连接/路由；没有可靠路由时禁用发送并解释如何恢复。不能靠匹配会话标题或最近一个 Bot 猜测接收方；页面上的“回复给 Codex”仅指回到**已登记会话对应的收件箱**，不承诺唤醒离线宿主。
8. 图片/附件显示真实可用性；上传的类型、体积、授权、失败恢复沿用原服务约束。旧记录缺正文、图片被清理或只保留哈希时说明“历史内容不可用”，不构造替代文本。
9. 管理端涉及删除会话或批量清理，应说明对手机页、任务卡片、收件箱和历史的影响。优先用归档；若执行永久删除，必须二次确认且符合现有删除语义和备份策略。
10. 手机 `/chat/` 继续保留独立入口与身份验证；管理端版本不能变成复制一份不同逻辑的会话系统，任一端新增特性应共享核心规则，视觉可分别适配桌面和手机。

**至少验收八个真实交互场景：** 正常回复；同一任务两端同时答复；网络超时后恢复查询；停用应用再打开旧会话；归档会话只读；较早消息深链定位；图片访问受控；外部 AI 不在线时正确解释“已入站/未领取”。

### 已确认决定 B：管理端可主动新建会话（本轮首版必须支持）

**确认来源：**用户明确要求“直接一步到位，支持新建会话”。此项与已确认的 A 方案同属**首版正式范围**，不再标记为未来可选功能；当前仍处于原型和产品评审阶段，**不授权 Codex 或服务器实施**。

**产品操作流程：**

1. 在“会话中心”点击 **新建会话** → 选择有权限的接入应用（如 Codex、Claude Code、服务器程序）→ 可选填写会话名称 → 编辑并发送第一条消息。初始未提交时保留草稿，优先避免因反复打开新建窗口而生成无意义空会话。发送后进入该会话时间线。
2. 新会话会出现在**同一份管理员与手机端历史**中，后续可继续发送、接收回复、查看任务卡片和关联投递详情，支持重命名、置顶、搜索与归档。不是管理端单独维护一套“客服对话”数据库。
3. 发送前展示明确的目标接入应用、可用收件方式和最后可验证活动，不把“应用已登记”当成“当前 AI 在线”。如果对方没有任何可用收件方式，说明原因、禁用发送或提供明确的仅保存草稿选项，不能暗中丢消息。
4. 新会话在服务端**归属于所选接入应用**，使用中转站生成的稳定会话标识；创建和第一条消息写入必须防止重复点击/网络重试产生重复会话或首条消息。用户不能通过伪造应用 ID 把消息送到未授权对象。管理员授权与应用 Key 仍然分离。
5. **投递能力如实表达：**支持事件订阅/主动接收的客户端可以尝试实时通知；仅支持 MCP/HTTP 主动拉取的程序通过既有收件箱领取。对于离线或未连接的 Codex/Claude Code，允许保存到目标应用收件箱（若该应用具备收件能力），但不承诺自动启动进程、恢复原宿主聊天窗口或执行消息中的指令。
6. **状态至少区分：**中转站已保存、等待客户端领取、客户端明确确认领取、客户端报告处理结果；若现有协议缺少领取确认，只能显示有证据的状态，不得根据轮询读取动作推断业务已经处理。若客户端长时间未领取，可以展示等待和诊断，不自动生成重复会话、重复命令。
7. 创建会话属于受保护的管理写操作，必须有管理员认证、同源/CSRF 保护、目标应用权限与防重放检查；用户输入按不可信内容处理，不能把“给 Codex 发消息”升级成不受控的远程命令接口。
8. **既有能力复用边界：**当前源码已存在客户端 `POST /api/conversations` 注册与 `GET /api/inbox` 收件、手机端回复接口，但**管理端主动创建并发首条消息的完整流程尚未视为已实现**。后续实施应复用会话登记、收件箱、回复账本与历史展示，补管理员创建入口及其专用权限/幂等规则，而不是新增第二套会话模型。

**新增原型必测场景：**新建并发送首条消息；按应用权限筛选收件目标；多次点击/断网重试；对方在线可领取与离线仅排队的提示；从手机端继续同一新会话；客户端停用或撤权后的只读/禁用反馈；目标不具备收件能力时禁止虚假“已发送”；返回列表保留会话定位。

| UX-24 | 有操作但无法理解操作后影响 | Key 撤销、删除连接、迁移默认通道、停用应用、归档/删除会话提供影响范围及取消路径；操作前用业务语言说明 | 高风险交互 |
| UX-25 | 管理端能回复但没有说明回复对象是否在线 | 发送前明确会话归属与可用性，发送后分“中转站已保存/客户端已领取/实际处理”；不能把读取当执行 | 会话闭环 |
| UX-26 | 管理端与手机端同时答复任务可能互相覆盖 | 一份权威决定，二次提交同决定幂等、异议冲突可见；统一 single/multiple/confirm/input/form 的校验和草稿 | 核心安全行为 |
| UX-27 | 目前登录/验证码演示太容易让人误解为真实上线能力 | 全原型显式模拟水印和能力说明，禁止保留演示凭据到生产；登录错误、旧密错误、会话过期与验证码用尽都有模拟反馈 | 原型安全语义 |
| UX-28 | 头像、退出、帮助出现在多个不同位置 | 头像统一放右上角，个性设置归账号；帮助/教程可独立入口；侧栏保持业务对象与系统级入口 | 跨页导航 |
| UX-29 | 操作完成后往往丢失筛选和原来的会话定位 | 返回保留搜索词、过滤器、页码与会话消息锚点；从总览、连接、应用、投递均可准确返回现场 | 交互细节 |
| UX-30 | 缺少统一的表单校验与网络响应反馈 | 每条流程给出未填写、校验失败、请求中、成功、已保存未生效、部分成功和结果未知的明确状态 | 交互组件 |
| UX-31 | 窄屏管理页常挤压标签、显示过多字段 | 改抽屉导航；桌面表格适度密度与必要横向滚动；窄屏详情优先、长表格变分层卡片 | 适配与易用 |
| UX-32 | 消息卡片可能因富文本而产生跨平台落差 | 统一标题/摘要/正文/字段/动作的消息语义，按连接能力降级，并提供真实客户端验证标识 | 后续协议设计 |
| UX-33 | 不同刷新动作可能造成“看起来已更改，但事实没变” | 当前生效配置与待提交草稿分离；刷新后持久值可验证；不可用时保留上次有效状态和诊断 | 设置与代理 |
| UX-34 | 未定义谁可以删除记录、附件何时清理 | 明确归档、删除、定期清理、备份保留及下载权限之间的关系；展示实际保存范围 | 产品规则+后端 |

| UX-39 | 新增通信连接、应用时缺乏针对性的下一步指引 | 首次完成才展示引导；已有应用的操作使用简短就地建议；帮助随时可找但不长期霸屏 | 引导策略 |

| UX-46 | 新会话列表和手机会话列表可能各自独立 | 复用同一历史与会话索引；新建、继续回复、重命名、归档跨端一致 | 共用数据与回归验收 |



## 6. 账号与安全实现需要提前想清楚

1. 单管理员账户的首次初始化与现有管理员 Key 的迁移路径；不能直接把 Key 当弱口令，也不能发布原型里的演示密码。
2. 用户名修改应验证当前密码并检查重名/合法性；改密需旧密码，成功撤销旧管理会话，不误撤销客户端 API 身份。
3. 忘记密码仅发往事先经过验证的本人微信/飞书；验证码限时、一次性、限尝试、限速；后台对找回请求统一反馈，避免泄漏账号状态。
4. 当前有效的最后一个恢复连接：站内多入口受控保护停用/删除/换绑；站外平台不可达时仍保留授权服务器 CLI 兜底；后端必须真执行，不只是按钮禁用。
5. 新管理会话与 `/chat/` 手机 Cookie 路径、应用 API Key 相互隔离；新增会话中心时认证和 CSRF 单独审核。
6. 私密 Key 不在日常管理页无限回显，不因导出包或 Codex 助手而输出日志；生产备份主密钥不可因重置管理密码而变化。

## 7. 工程与运行护栏（与 UI 设计独立实施）

- 复用此前已发现的三项定点可靠性问题：默认微信发送锁影响其他操作、手机答复不同步飞书卡片、获取飞书令牌前失败被误分为投递结果未知；在当前升级分支定点核查与修复，加相应回归。
- 全局投递查询与管理员会话查阅需新增受控读接口；已有 `/chat/` 历史页与记录模型是复用基础，避免第二份聊天数据库。
- 分清“桥已接受请求 / 平台已接受 / 本人确认 / 客户端已读取 / 业务执行完成”，不能统一显示“成功”；未知结果不凭新去重键绕开。
- 存储和历史策略包括记录分页、删除/归档保留、敏感正文展示、附件访问、备份中的历史数据边界。
- 改代码前检查当前生产基线（已保护 stable/2026-10-14-production-1.16.0）、生产数据最新备份、隔离分支；原型不得连真实服务或更换生产凭据。
- 重要交互与兼容行为测试：API Key 重置/撤销、最后恢复通道保护、手机与管理端会话读取/回复互不串扰、消息深链定位、重复提交、旧数据、窄屏和 Windows 离线双击。

## 8. 建议先确认设计，再分批落地

**设计确认轮（只改原型与方案）**：统一导航、总览、可新建/回复/处理任务的完整会话中心、投递记录、接入应用 Key、连接保护、账号入口、代理页面、窄屏/空态/异常状态。原型需能点击、真实路径与返回现场一致；包含完整模拟数据集，禁止装成实时服务。此阶段不更改生产、不重构后端。

**实施 A：日常沟通与诊断闭环**：接入应用 → 投递 → 记录 → 管理员主动新建会话/首条消息/继续回复/任务答复；优先修与此相关的真实缺陷。服务端先落实管理认证和写权限边界，不得把“仅以旧管理 Key 访问只读诊断”直接视为公开可用的写能力。新会话页面复用旧服务与组件。

**实施 B：连接与凭据闭环**：新增或管理连接 → 验证收发 → 授权 → Key 轮换/应急撤销 → 账号与恢复保护。涉及敏感认证与数据迁移，单独技术验收。

**实施 C：维护和交付闭环**：代理出口、状态与恢复、三类接入/维护资料、离线安装与受控 AI 配置流程；新 AI 实测接入。

**最后再考虑**：跨平台多投递策略、更多通信平台、复杂富文本模板与附件、自动化协作和通知聚合。这些都应基于确认后的统一协议，不抢占本轮页面整理。

## 9. 验收口径

1. 用户不用读代码，能在管理端独立找到应用、连接、会话、发送异常、密钥轮换和个人账号入口。
2. **已确认会话中心首版支持主动新建会话、发送首条消息、继续回复和处理任务**；管理端与手机端引用同一历史与答复逻辑；同时提交只有一份决定；管理员浏览不错误地清空手机未读或改变外部程序执行状态；任何来源均有明确归属/未归属说明。
3. 不以“界面上有按钮”冒充后端已经完成；原型、已实现、待实施三者清楚标记。
4. 完整业务流程验收，而不是只验单页截图。未配置、空数据、失败、结果未知、取消、重试、旧记录、窄屏都覆盖。
5. 先完成候选方案确认后再生成一次合并执行要求；Codex 按可回退批次交付，不允许擅自开始生产部署或大型架构重写。


## 10. 再次核查后补充的跨页面设计规则

### A. 用户真正操作的“对象”必须稳定

- 接入应用、应用凭据、通信连接、消息、投递尝试、会话、任务与回复有明确的主从关系。**一个应用可以有多个会话；一条消息可以有多个渠道投递记录，但不因此产生多个逻辑决定**。
- **会话的归属以登记的 conversation_id / client_id 为准**，不能靠同名应用或平台标签自动合并两个不同会话。对于没有关联到会话的外部入站，展示“未归属”，不猜对应 Codex。
- 管理界面显示友好名称，详情保留可复制的稳定 ID。改名不改变身份或路由；Key 轮换不改变应用的会话归属；旧消息关联原发送连接，不因后来改默认连接而改变历史。
- 在有多个连接时，回复出口、通知默认出口和恢复通道是三个不同配置。页面必须明确显示当前选择及其作用域。

### B. 一处编辑，整个管理端都必须有一致解释

- 从应用详情查看连接时应带上该应用的授权视角；从连接详情查看应用时要显示哪些应用依赖它。影响范围可在停用/删除前查验，不能只弹一句“确定吗”。
- 从会话点击消息应按准确记录跳到投递明细；从投递明细返回会话要保持消息位置。从总览进入失败队列要保留筛选。没有关联关系时提示原因，不硬造跳转。
- 任何高风险动作都应分清“保存草稿、实际生效、最终验收”。尤其是代理节点切换、机器人测试、密钥轮换与管理员恢复绑定。
- 操作界面统一使用明确的成功/失败/未知状态及证据时间；遇到部分成功时不可用一个笼统“保存失败”抹掉已经成功保存的业务事实。

### C. 会话中心桌面端应怎么用

1. 左侧：按应用/时间/待处理筛选的会话列表，支持搜索、未读/待办、置顶、归档；中间：时间线、发送状态、各种任务卡片；右侧仅在需要时展开消息技术详情（不常驻占屏）。
2. 会话顶部固定“应用名称 / 会话名称 / 当前是否可回复 / 回复回到哪里”，并显示可追溯会话 ID；不要用伪“Codex 在线”状态，除非实际有宿主在线证据。
3. 底部回复区沿用旧网页文本/图片能力及必要上传约束。普通回复与任务卡片答复两个入口明确分开，发送中防止重复点击，失败后留存草稿。
4. 已答复任务不再次让管理员提交新选择。完成/失败/取消、未领取和处理中由原调用方报告；仅对真正可修改的状态开放控件。
5. 当手机和管理端显示同一条消息时，时间、正文、任务状态来自同一事实源；管理端查看行为不会改变手机未读指针。管理端自身未读设计若复杂，可暂不加独立未读，先展示待答复数。
6. 对长会话要能加载更早内容、返回最近消息、深链定位历史；列表搜索和正文搜索分开说明范围，避免“一搜不到”误解为记录丢失。
7. 演示会话数据应覆盖单向告警、正常交互、表单任务、处理失败、客户端停用、无关联入站、跨端提交冲突、旧消息缺失正文等情况。

### D. 视觉和交互统一规则（供原型，不硬编码具体像素）

- 页面视觉主线统一：标题/用途简述 → 主操作 → 筛选或状态 → 列表/详情 → 次要说明。高频操作在主层，密钥、App Secret、Webhook 等技术字段可按需展开。
- 建议采用中等信息密度。大面积空白、过浅提示文字与大量小字号不能混用；按钮主次、危险动作和状态色应有一致规则，不靠颜色单独传达信息。
- 抽屉、弹窗、步骤向导的“关闭/取消/上一步/返回现场”语义保持一致，未保存内容在离开时提醒；需要长篇说明的内容移到帮助抽屉，不挤在主要表单区。
- 桌面/窄屏均要实查，至少验证 1440px 桌面与约 390px 手机视口；键盘导航、焦点、文字对比与错误关联也要覆盖。不能只用截图证明交互完成。
- 管理原型必须有醒目的“模拟数据/未连接服务”标识；所有可点击主操作应展示明确结果，后端尚未实现的功能不能假装已在真实系统启用。

## 12. 需求与决策台账（避免让 Codex 猜答案）

### 已明确确认，不再反复询问

- Notify Bridge 是统一消息中转站，不转型任务平台或内置 Agent。
- Codex/Claude Code 充当站外维护与接入助手；正式服务不依赖它们在线。
- 核心管理对象：接入应用、通信连接、投递规则、消息和回复，任务卡片是消息交互扩展。
- 会话中心进入一级导航，与投递记录分开；**管理端能查看已记录全文、直接回复和处理任务（A）。**
- 管理员的用户名与密码操作在右上角账号入口；设置与帮助分离。
- 稳定版本与生产备份不受此次原型影响；本阶段没有授权运行 Codex 改正式代码。

### 本轮按专业默认提出的候选，尚不假冒用户已批准

- 会话中心首版仅回复**已经登记且可写的会话**，不主动创建一个新的、无关联的 AI 会话。
- 管理端只浏览历史不会更改手机已读位置；普通回复与任务答复是不同交互；记录操作来源。
- 总览基于实际首次接入状态决定是否显示引导，成熟用户以异常/待处理为第一视觉层。
- 密钥不允许日常无限复制旧明文；使用 Key ID 识别归属，新 Key 可在创建时一次复制，并支持未来受控轮换。
- 新版原型一次性整体梳理视觉与流程，但正式实现仍按**完整端到端使用场景**切分，逐批测试与交付。

### 尚需后续真正决定的产品问题

**唯一建议先讨论的高杠杆问题：**会话中心除了回复已有会话，是否还需要让管理员主动发起一条全新会话（例如主动对某个 Codex 说“开始检查”）？

- **推荐初版不做**：现有通知桥的会话需要外部程序登记，主动发起还涉及宿主接收/是否在线、会话路由、身份和执行授权；直接加“新建聊天”容易把中转站推向通用 Agent 平台。
- 若只想主动给已有会话再发一句话，可以在确认其接收机制与权限后按正常回复处理，不新增 Agent 执行能力。
- 这个决策不阻止当前其余页面原型设计，暂按“回复已有会话”作为候选范围即可。

## 10. 本次确认的影响与未决边界

- **已决定**：首版必须主动新建会话，不再把它视作第二期/长期规划；保留 A 方案的回复和任务操作。
- **当前不需要另行决策的默认**：只能选择已登记且有收件权限的接入应用；新建默认从管理员发起并写入同一会话账本；新会话也出现在原手机端。
- **后续实现中需据能力验证**：是否能实时通知特定 Codex/Claude 宿主、可否恢复其原有聊天上下文。若宿主不支持，不因此取消“新建并排队至收件箱”，但界面应明确限制。
- **未授权事项**：不修改原型、业务代码、生产部署和真实消息连接；待整体体验审查收口后一次性向 Codex 交付实施要求。
