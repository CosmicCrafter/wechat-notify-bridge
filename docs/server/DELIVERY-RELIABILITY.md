# 微信推送限制与失败诊断

## 2026-10-04 的排查结果

线上时间线显示：同一微信上下文先有 10 条被接口接受的推送，随后第 11 条被微信以 `-2` 拒绝；最后一次微信发言距失败约 6 小时 40 分钟。用户直接从微信发来新消息后，新发送恢复。更早的一次失败也发生在累计 10 条之后。另一次失败前只记录到 9 条成功推送，因此不能把全部 `-2` 都归为同一个固定额度错误。

**本次最强的解释是主动推送额度限制，尚不能确认微信内部判定。** 旧版本只保存错误码，未保存上游 `errmsg`，无法补回当时的原始错误说明。不要把“新消息后恢复”直接当成已证明 token 按某个固定时长过期。

证据来源与边界：

- [腾讯的协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)：回复沿用微信入站消息的 `context_token`；接口层的返回值不等于手机收件。
- [pushplus 自有渠道说明](https://www.pushplus.plus/doc/channel/clawbot.html)：该接入方说明每下发 10 条后需主动对话，且每隔 24 小时需主动对话。这与本项目观察相符，但不是腾讯对本项目的稳定额度或 TTL 承诺。
- [腾讯仓库问题 #270](https://github.com/Tencent/openclaw-weixin/issues/270)：报告 `ret=-2` 与 `errmsg=rate limited`。
- [腾讯仓库问题 #309](https://github.com/Tencent/openclaw-weixin/issues/309)：报告 `ret=-2` 与 `errmsg=prepare failed`，用户发言后恢复。这是用户实测报告，不能据此认定统一过期时长。

## 1.14.0 起的诊断

每次真实发送保存一份诊断，与原 `dedup_key` 回执关联。新回执的 `diagnostics` 包含请求长度、UTF-8 字节数、上游 HTTP 状态、业务 `ret`/`errcode`、请求用时、发送时上下文年龄，以及当时本地记录的已接受推送数。重启后仍可查询；旧回执的该字段为 `null`，不伪造历史证据。

上游错误说明限长后加密保存，不返回任意上游文本。MCP、API 和普通日志只显示固定分类和说明，避免错误响应中的敏感信息泄露。删除对应网页会话时一起删除加密诊断，保留必要的去重墓碑。

| 分类 | 可得出的结论 |
| --- | --- |
| `wechat_rate_limited` | 上游错误说明明确提到限流；不推测具体额度或重试时刻 |
| `wechat_context_rejected` | 上游错误说明明确提到上下文无效、缺失或过期 |
| `wechat_session_expired` | 微信返回 `-14`，按原账号重新绑定 |
| `wechat_prepare_failed` | 上游返回 `prepare failed`；无法区分额度、上下文或其他准备失败 |
| `wechat_rejected` | 其他业务拒绝，包括没有错误说明的 `-2` |
| `network_timeout` / `network_error` / `http_error` / `invalid_response` | 请求或响应出错，实际投递未确认，不能自动重发 |

`getCallerIdentity`、HTTP `/api/status` 和 Admin 显示微信上下文最近更新时间、此后接口接受的推送数及最近发送诊断。达到本地记录的 8 条时提示可能接近主动推送限额；这个计数不包含其他进程发送，也无法预测微信额外的限流，**不是服务端的剩余额度**，不会强制阻止第 11 条。

## 运行原则

1. 接收正常与发送成功分开判断。`connection_status=connected` 只说明入站轮询正常；检查 `last_send_status`、`send_recovery_hint` 和原发送回执。
2. 12 小时心跳只是一次主动消息，会占用发送机会；它不会获取新的微信上下文，不能保证长期推送权限。网页回复、点击消息链接、查询状态也不会在本项目里刷新微信上下文。
3. 拒绝和超时都保留原记录，不换去重键、不无限重试。新微信消息不代表历史失败消息已经补发；本项目尚无自动补发队列。
4. 平时减少碎片推送，将同一任务的更新合并；看到额度提示时直接在微信 ClawBot 发一句话，再以新的实际发送结果确认恢复。
5. 必须送达的关键告警，应由调用程序明确处理失败与结果未知，并配置独立的备用通知渠道。接入备用渠道需要单独配置，本服务不会自行给第三方发消息。

本次没有为了复现而耗尽真实账号额度。分类、计数、加密、重启、网页回复隔离与去重使用 MockTransport 验证；下一次自然出现的拒绝将获得可核对的上游说明。
