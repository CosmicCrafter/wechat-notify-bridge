# 新增飞书 Bot 操作指南

本指南记录 2026-10-12「开票助手」实际创建、发布和双向验收的流程，适用于通知桥中新增独立的通知、审批或回复机器人。飞书后台界面后续可能变化，以实际页面为准。

> **给 Codex 的入口指令**：用户说“给我新增一个 XX 飞书 Bot，用于通知、审批和回复”时，按本文执行完整接入，不要只创建飞书应用。先读下方「Codex 执行手册」，再按各步骤操作。除登录、权限确认、凭据生成或手机验收等实际需要用户参与的环节外，连续完成已授权工作。

## 一、先分清三个身份

| 名称 | 作用 | 从哪里取得 |
| --- | --- | --- |
| App ID / App Secret | 飞书应用身份和凭据 | 飞书后台 → 凭证与基础信息 |
| bot_id | 通知桥中具体的 Bot 连接 | 通知桥 → Bot 管理，或已授权客户端的 `/api/status` |
| 客户端 Key | 程序 / AI 调用通知桥的凭据 | 通知桥 → 接入密钥 |

**新增一个飞书 Bot，要新建一个飞书企业自建应用，再在通知桥创建对应连接。** 可以沿用旧 Bot 的配置流程，但不能复制旧应用的 App Secret、Open ID、Encrypt Key 或完整回调地址。

当前每个 Bot 配置一位本人接收者，支持本人私聊；本指南不涉及群聊、外部用户或飞书原生审批平台的审批流。卡片提交只把决定交回调用程序，真正的开票、作废等业务由业务系统执行并校验。

## 二、准备入口和顺序

- [飞书开发者后台](https://open.feishu.cn/app)：需要应用创建、配置和发布权限。
- 通知桥管理页：`https://你的域名/bridge/admin/`。
- 当前自用部署：[Bot 管理](https://notify.sci-pi.cn/bridge/admin/#bots)、[接入密钥](https://notify.sci-pi.cn/bridge/admin/#keys)、[开发者文档](https://notify.sci-pi.cn/bridge/admin/#developer)。其他部署请替换域名及实际路径前缀。

顺序：**创建应用 → 机器人能力与权限 → 获取凭据和本人 Open ID → 通知桥保存配置 → 飞书验证回调并订阅 → 发布 → Key 授权 → 三项实测。**

通知桥必须先保存完整配置，飞书才能验证回调地址。只填写地址、没有发布订阅，也不能完成消息接收。

## 三、创建应用与机器人能力

1. 在飞书开发者后台选择正确企业，点击「创建企业自建应用」。不要选群聊中的自定义 Webhook 机器人。
2. 填写名称、描述、图标。例如「开票助手」，描述为「用于开票业务的通知推送、审批卡片与消息回复」。
3. 在「添加应用能力」中添加「机器人」。
4. 在「权限管理 → 开通权限」选择 **应用身份权限**，开通以下两项：

| 权限标识 | 页面名称 | 用途 |
| --- | --- | --- |
| `im:message:send_as_bot` | 以应用的身份发消息 | 发通知、发送及更新卡片 |
| `im:message.p2p_msg:readonly` | 读取用户发给机器人的单聊消息 | 接收本人发给 Bot 的文字 |

这次接入用上述两项即可；不要为了复制配置直接导入其他应用全部权限。卡片回传还需要后面的回调订阅。

## 四、取得新应用自己的凭据和 Open ID

### 应用凭据与加密策略

- 「凭证与基础信息」：取得 App ID、App Secret。
- 「事件与回调 → 加密策略」：生成并保存 Encrypt Key，取得 Verification Token。
- 把这些值填到通知桥的该 Bot 配置中，必须与当前飞书应用逐项对应。不要把密钥写进说明文档、Git、截图、公开压缩包或聊天。

### 获取本人 Open ID

**同一个人在不同飞书应用中的 Open ID 可以不同。不能复制另一 Bot 的本人 Open ID，也不能盲目使用管理页预填的默认值。**

1. 打开 [API 调试台](https://open.feishu.cn/api-explorer)，切换到刚创建的应用。
2. 选择「消息 → 发送消息」，将 `receive_id_type` 设为 `open_id`。
3. 点击「快速复制 open_id」，搜索并勾选本人，再点击「复制成员 ID」。
4. 得到 `ou_…` 格式的值，填入通知桥「本人 Open ID」。

这里只使用成员选择器，不必点击「获取 Token」或「开始调试」，也不需要实际发送示例消息。如果通过带 App ID 的地址打开调试台后出现切换提示，先确认切换，再核对页面左上角应用名称。

## 五、在通知桥创建连接

1. 打开「Bot 管理 → ＋ 添加 Bot」。
2. 填写名称，平台选择「飞书应用机器人」，点击「创建并配置」。
3. 填写以下内容并启用、保存：

| 字段 | 填写内容 |
| --- | --- |
| App ID | 新应用的 `cli_…` |
| App Secret | 新应用的 Secret |
| 本人 Open ID | 在新应用上下文复制的 `ou_…` |
| Verification Token | 新应用加密策略中的值 |
| Encrypt Key | 新应用加密策略中生成并保存的值 |

4. 复制管理页显示的该 Bot 专属回调地址，例如：

```text
https://你的域名/bridge/channels/feishu/<bot_id>/callback
```

`<bot_id>` 是通知桥 ID，不是飞书 App ID。不要复制其他 Bot 的地址，也不要只把旧地址里的 `wechat` 换成 `bridge` 后就假设正确。以当前管理页给出的完整地址为准。

当前部署保留旧 `/wechat` 入口用于兼容；新接入优先使用 `/bridge`。飞书和微信通信直连，不经过面向 OpenAI 回调的代理。

## 六、分别配置消息事件和卡片回调

这两页是独立配置，**必须都做**。同一个 Bot 两处填写相同回调地址。

### 事件配置：接收文字回复

1. 飞书「事件与回调 → 事件配置」，编辑订阅方式。
2. 选择「将事件发送至开发者服务器」，填入通知桥显示的地址并保存。
3. 校验通过后点击「添加事件」，搜索并添加 `im.message.receive_v1`（接收消息）。
4. 确认列表中已出现该事件，读取机器人单聊消息权限显示已开通。

### 回调配置：接收卡片按钮操作

1. 切换到「回调配置」，编辑订阅方式。
2. 选择「将回调发送至开发者服务器」，填相同地址并保存。
3. 点击「添加回调」，选择 **卡片回传交互 `card.action.trigger`**。
4. 不要选「消息卡片回传交互（旧）`card.action.trigger_v1`」。

本项目使用 HTTPS 回调模式；不要选「长连接」，除非另外实现并部署了对应接收端。

## 七、发布使配置生效

1. 点击「创建版本」，填写版本号（首次可用 `1.0.0`）及更新说明。
2. 确认移动端和桌面端默认能力均为机器人。
3. 可用范围至少包含接收通知的本人。个人使用可先仅开放给本人；不要顺手开放全企业或外部共享。
4. 保存并确认发布。若企业要求审核，等待管理员通过；若页面提示免审，提交后仍要检查结果。
5. 确认应用显示「已启用」「当前修改均已发布」。以后修改事件订阅、权限等配置，也要检查是否需要再次发布。

## 八、给调用程序授权

在通知桥「接入密钥」中，为开票系统或 AI 建立独立 Key，勾选新 Bot；已有 Key 则调整其 Bot 权限。**新增 Bot 不会自动授权给已有 Key。**

调用方配置：

```text
BASE_URL=https://你的域名/bridge
API_KEY=<该调用方自己的客户端密钥>
BOT_ID=<通知桥中这个Bot的ID>
```

1. 使用 `Authorization: Bearer <API_KEY>` 请求 `GET /api/status`，确认授权 Bot 列表包含新 Bot。
2. `POST /api/conversations` 登记会话并保存返回的 `conversation_id`。
3. 调用 `/api/messages`、`/api/notifications` 或 `/api/task-cards`，明确传入 `bot_id`、`conversation_id` 和业务事件唯一的 `dedup_key`。
4. 使用 `/api/inbox` 读取回复；任务卡片结果可通过对应任务查询接口核对。完整参数见 [API 文档](API.md)、[任务卡片](TASK-CARDS.md)、[多 Bot 授权](BOTS.md)。

客户端 Key 不是 App Secret，也不是管理页管理员密钥。发送超时或结果不明，先用原 Bot、会话和 `dedup_key` 查回执，不要换键重发造成重复审批。

## 九、必须分开验收的三项

| 验收项 | 怎么测试 | 通过标准 |
| --- | --- | --- |
| 通知送达 | 发一条无业务影响的测试通知或卡片 | 本人实际在新 Bot 聊天中看到；仅 `api_accepted` 不算手机确认 |
| 卡片回传 | 点击测试卡片「测试成功」 | 卡片更新，服务器任务为 `answered`，答案与本人选择一致 |
| 普通文字 | 在聊天底部输入框单独发「开票回复测试」 | 服务器收到 `source=feishu` 且 `bot_id` 对应新 Bot 的文本 |

注意：

- 点击卡片按钮不等于发送了一条普通文字消息；两项必须分别验收。
- 已提交的卡片不能再次提交。需要复测时创建新的测试卡片和事件键，不复用真实审批。
- 普通无标签文字可能进入 Bot 公共收件箱，并不自动属于某个程序会话。引用目标通知回复，或使用 `[客户端-会话] 内容`，可明确路由。需要验证业务会话接收时，应另测引用回复。
- 查询指定会话的收件箱看不到公共消息，不代表飞书没有投递；检查 Bot 对应的公共收件记录。
- `mode=input` 待输入任务另有自动匹配规则，见 [飞书双向通道](FEISHU.md#飞书输入任务聊天框直接回复)，不要与普通无任务的文字回复混淆。
- 有测试专用 Key 时，全部验收结束后停用；正式业务 Key 单独配置。不要把测试卡片提交当成真实开票或下载授权。

## 十、常见问题

| 现象 | 优先检查 |
| --- | --- |
| 保存地址报「Challenge code 没有返回」 | 通知桥已启用且配置完整；地址属于当前 Bot；Token/Encrypt Key 与当前应用一致；HTTPS 和路由能访问；查看服务端拒绝原因 |
| 发消息报 Open ID 跨应用错误（曾见 `99992361`） | 回到新应用的 API 调试台重新获取本人 Open ID，检查应用可用范围 |
| 能发送但收不到回复 | `im.message.receive_v1` 是否订阅并发布；本人私聊权限是否开通；消息是否真的发给这个 Bot；接收者 Open ID 是否匹配 |
| 卡片提示目标回调服务不在线 | 卡片回调是否配置且发布；服务和地址是否可达，不只检查消息事件页 |
| 卡片点击报 `200671` | 查飞书投递记录和服务端日志，该错误码不能单独确定根因；本项目曾因回调时间戳解析不兼容导致验签失败，现有修复支持对应格式，不能关闭签名校验来绕过 |
| 卡片已提交后不能再点 | 正常防重复行为，复测用新测试卡片 |
| 接口提示 Bot 无权限 | 检查这把客户端 Key 是否被授权使用新 Bot，不能只看管理员列表中有没有 Bot |
| 新 Bot 已配置，AI 却没自动回复 | 收件、会话路由和 AI 宿主唤醒是三个环节；安装 MCP 或新增 Bot 不会自动建立宿主唤醒绑定 |

排查入口：飞书「日志检索 → 事件日志检索」、通知桥 Bot 状态与对应收件记录、服务器日志。日志和截图不应包含 Secret、Token、Encrypt Key。

## 十一、留档清单

记录 Bot 名称、App ID、通知桥 bot_id、接收人对应关系、回调地址、发布版本、授权的客户端名称、三项验收结果即可。凭据仅保存在受控配置中。

## 十二、Codex 执行手册：从一句需求到跑通

### 12.1 确认环境，不重建已有连接

1. 将用户给出的用途转为简短 Bot 名称。例如“开票通知审批”可用“开票助手”；名称未定时可先采用合理名称，不必反复询问。
2. 阅读当前项目的 `AGENTS.md`（如有）、本文及 `docs/server/BOTS.md`。检查工作目录、当前代码和部署入口；本文记录的后台路径是此项目实现，不是飞书官方 API。
3. 使用用户已登录的飞书后台与通知桥。先查询现有 Bot，核对名称、平台和 App ID。若上次已创建一半，复用准确匹配的记录继续；同名不足以证明是同一应用。不要重复创建、覆盖另一个 Bot 或改现有身份。
4. 当前工作区既有部署管理凭据位于 `.private/wechat-admin.json` 的 `admin_key` 字段；仅在本机确实存在、属于目标服务且任务已授权时使用，绝不输出其值。其他机器通过管理员登录或受控配置取得凭据，不要假设这个文件存在。
5. 浏览器操作使用当前环境提供的浏览器工具；普通 UI 优先读最新页面状态后操作。不要复用本文操作过程中的旧元素编号，也不要用隐藏网页接口绕过登录或确认。

### 12.2 飞书部分的执行约束

- 创建应用、启用机器人、准备两项应用身份权限。按当前工具规则，在需要的权限授权点请求一次明确确认；同一范围已确认后继续，不反复问。
- 新认证凭据的生成如受浏览器工具“用户接管”规则限制，停在对应页面请用户生成。收到“已保存”后继续读取已有值并配置，不让用户把 Secret 发到聊天。
- 通过新应用的 API 调试台成员选择器获取本人 Open ID。复制后检查 `ou_` 格式、当前应用名称；若工具剪贴板读不到，不猜值、不用其他应用的值替代，应检查复制控件或让用户完成这一步。
- 保存 App ID、App Secret、本人 Open ID、Verification Token、Encrypt Key 到受控私有配置；不在工具输出、截图或报告中展示后三项秘密。
- 配好通知桥后，再保存消息事件地址、订阅 `im.message.receive_v1`；保存卡片回调地址、订阅 `card.action.trigger`。最后发布，检查“当前修改均已发布”。

### 12.3 通知桥管理接口（可替代管理页表单）

以下路径均相对于 `BASE_URL=https://你的域名/bridge`；每个请求用 `Authorization: Bearer <管理员密钥>` 和 JSON 请求体。管理员接口不属于普通客户端权限，不能用调用方 Key 替代。当前实现将管理接口从公开 OpenAPI 隐藏；维护时以 `server/src/wechat_bridge/api/admin.py`、`api/channels.py` 为准。

| 顺序 | 方法与路径 | 操作与核验 |
| --- | --- | --- |
| 1 | `GET /admin/api/bots` | 返回 `bots`，先查是否已有准确匹配的连接 |
| 2 | `POST /admin/api/bots` | `{"name":"开票助手","platform":"feishu"}`；保存返回 `id` 为 bot_id |
| 3 | `GET /admin/api/bots/{bot_id}/feishu` | 读取已有配置判断断点；响应可能含完整凭据，禁止整体打印 |
| 4 | `POST /admin/api/bots/{bot_id}/feishu` | 按下方结构保存完整配置；核验 `enabled`、`configured`、`app_id`、`owner_open_id` 和 `callback_url` |
| 5 | `POST /admin/api/clients` | 为明确的调用程序创建 Key，并指定允许的 Bot；原始 Key 只安全保存，不输出 |
| 6 | `GET /admin/api/clients/{client_id}/bots` | 调整已有 Key 前先读取现有授权 |
| 7 | `POST /admin/api/clients/{client_id}/bots` | 提交完整 `bot_ids` 和 `default_bot_id`；此操作是替换列表，必须保留仍需的旧授权，默认 Bot 不擅自更换 |

保存 Bot 的请求结构：

```json
{
  "enabled": true,
  "app_id": "<新飞书AppID>",
  "app_secret": "<新飞书AppSecret>",
  "owner_open_id": "<新应用下的本人OpenID>",
  "verification_token": "<新应用VerificationToken>",
  "encrypt_key": "<新应用EncryptKey>"
}
```

开启前五项必须齐全。当前实现第一次写入后固定 App ID 和本人 Open ID；错填后会出现 `feishu_owner_mismatch`，不要直接改数据库绕过身份隔离，应核对新建连接或专门迁移。另一 Bot 已绑定相同 App ID 会返回 `bot_binding_conflict`。因此 **不要先把其他应用的默认 Open ID 保存进去再改**。

建立调用方授权的请求：

```json
{
  "name": "开票系统",
  "bot_ids": ["<新BotID>"],
  "default_bot_id": "<新BotID>"
}
```

返回包含 `client`、`api_key`、`base_url`。已有业务 Key 只补充授权；未明确业务调用方时，不猜哪把 Key 属于该业务。可先创建仅授权新 Bot 的“接入验收”临时 Key 完成测试，再停用；最终报告明确正式调用方是否已授权，不能把临时测试 Key 当正式对接。

### 12.4 用普通客户端接口做一次完整验收

下面请求改用 **客户端 Key**，不能继续使用管理员密钥。

登记会话：`POST /api/conversations`

```json
{"conversation_key":"<本次验收的稳定唯一标识>","name":"接入测试"}
```

保存返回的 `id` 为 conversation_id。创建卡片：`POST /api/task-cards`

```json
{
  "bot_id": "<新BotID>",
  "conversation_id": "<刚登记的会话ID>",
  "dedup_key": "<本次卡片的稳定唯一事件键>",
  "title": "新 Bot · 接入验收",
  "prompt": "仅测试通信，不涉及真实业务。请点击测试成功，然后在聊天底部输入框单独发送：文字回复测试。",
  "mode": "single",
  "options": [
    {"id":"ok","label":"测试成功"},
    {"id":"issue","label":"发现问题"}
  ],
  "allow_custom": false,
  "expires_in": 86400
}
```

单选卡必须有 2–8 个选项，不能只有一个按钮。保存响应 `task.id`、发送状态和原 dedup_key。结果未知时先查 `GET /api/deliveries?bot_id=...&conversation_id=...&dedup_key=...`，不要自动生成新键重发。

用户反馈后检查：

- `GET /api/conversations/{conversation_id}/tasks/{task_id}`：`task.status=answered`、`task.answer.choice_id=ok`。
- `GET /api/inbox?conversation_id=...&after_id=...&include_unaddressed=true&limit=100`：核对卡片 `task_response`、普通文字、`source` 与 `bot_id`。记录游标，不把查询结果中其他消息误算成本次验收。
- 当前 `/api/inbox` **不传 conversation_id 时只取未明确路由消息**，不是所有会话的总列表；指定会话并带 `include_unaddressed=true` 才能同时检查该会话和公共收件。
- 若普通文字无记录，先检查飞书发布状态及「事件日志检索」，再检查服务端投递和过滤原因。向用户说明“在聊天输入框发送文字”和“点卡片”是两件事。不要把卡片成功当作文字收件成功。
- 若业务需要会话级回复，另让用户引用目标通知发送测试文本，确认 `route_status=direct` 且 conversation_id 正确。普通无标签消息进入公共收件只证明 Bot 收到，不证明已路由到 AI。

完成后通过 `POST /admin/api/clients/{client_id}/revoke` 停用临时测试 Key（用管理员认证，仅处理本次测试 Key）。保留测试记录，不动正式调用方或历史审批。测试尚未结束时不要提前撤销，否则无法继续读取回传。
