# Windows 桌面消息唤醒（实验性）

适用场景：Codex 桌面正在运行，指定聊天已登记，用户明确启用微信/手机网页回复唤醒。无需模型定期读取收件箱；本机程序每 3 秒检查服务器消息编号，仅新消息触发桌面消息工具。

服务端需 1.5.2 或更高。云端 MCP 连接本身不会启用本机唤醒，也不支持在桌面退出后自动启动应用。

## 显式绑定

在私有目录保存 `binding.json`，不写密钥：

```json
{
  "conversation_id": "桥接服务已登记的会话ID",
  "thread_id": "对应的Codex聊天ID",
  "app_tools_server": "当前已安装的codex-app-tools目录/server.mjs"
}
```

从 Codex 提供的执行环境运行（继承 `CODEX_APP_TOOLS_PIPE_PATH` 和 Node 路径），并配置已有的 `WECHAT_NOTIFY_CREDENTIAL_FILE` 或 HTTPS API 环境变量：

```powershell
python server/desktop_relay.py --binding 私有目录/binding.json --state 私有目录/relay.sqlite3
```

在 Windows 使用隐藏窗口运行时，指定 `Start-Process -WindowStyle Hidden`。每个绑定使用独立状态文件。已有进程持有文件锁时，第二个进程会退出。停止对应接收进程即可暂停；下次使用相同配置和状态文件恢复。

首次成功连接只保存当前位置，避免重新处理历史。启用后的事件及游标写入 SQLite；程序停止期间的新消息保留在服务器，恢复后读取。API 无法访问时重试，不调用模型。仅监测指定会话的直接消息，公共收件箱、管理命令、机器人发送和心跳不会触发。

## 投递状态

- `pending`：等待投递。
- `dispatching`：正在调用桌面工具。
- `submitted`：桌面工具接受，不代表 AI 已完成。
- `uncertain`：中断或失败后无法确认投递结果；暂停此绑定后续投递，需核对聊天后人工处理，禁止盲目重试。

SQLite `state` 表保存游标、最近状态及更新时间；`events` 只保存消息编号和状态，不保存正文或密钥。轮询接口不会把正文标成已读，AI 使用 `getMessages` 后才产生现有“客户端已读取”状态。

## 当前限制

此适配器复用桌面自带 MCP 的内部接口，并非官方承诺稳定的外部 API。桌面升级、退出重开、管道或缓存路径变化后，需要从新的桌面执行环境重新启动接收器。当前不自动开机启动，不扫描其他进程管道，不修改应用缓存，不另起 Codex 推理实例。

桌面忙碌时沿用其原生消息投递行为，可能进入当前回合；本程序不声称已实现“等待整个任务完成后再回复”的调度。超时歧义采用暂停保证不盲目重复，不能宣称跨宿主崩溃的严格 exactly-once。

微信消息仍保留外部来源。路由和唤醒不赋予附件、引用或第三方转述额外权限。用户取消订阅时，停止接收器；也可停用桥接会话，使轮询被服务端拒绝。
